# Data Snapshot Metadata Schema Validation 2 Protocol

**Status:** Protocol for calibration and execution  
**Baseline:** Data Snapshot Metadata Schema v1.1.1  
**Relationship to Validation 1:** Confirmatory coverage assessment using the same snapshots held out from initial schema discovery

## 1. Research question

For each data snapshot:

> Given Data Snapshot Metadata Schema v1.1.1, this snapshot, and its parent-document context, is there any critical or possibly critical reusable metadata information about the snapshot that is not adequately covered by an existing schema field and whose absence would materially impair interpretability, discoverability, or both?

At the study level, Validation 2 asks whether adding the 202 held-out validation snapshots to the original 210-snapshot discovery corpus would have changed the accepted 36-field schema inventory.

## 2. Validation design

Validation 2 is confirmatory rather than a second residual-mining exercise.

- Schema v1.1.1 is frozen during validation.
- The model assesses one snapshot per request.
- The complete schema and parent-document metadata are supplied with the image.
- The model returns only critical or possibly critical coverage gaps.
- The model does not inventory covered information or generate speculative extensions.
- Field acceptance remains a human decision.
- Validation 2 does not resume the separate Schema v1.2 standards-alignment workstream.

The 202 snapshots remain held out from the original schema-discovery sample. Validation 2 reuses the Validation 1 snapshots and therefore supplies a different confirmatory assessment of the same held-out evidence rather than an independent second sample.

## 3. Sample reuse and reproducibility

The directory supplied as `SNAPSHOTS_DIR` defines the input set for each run. Calibration0 and Calibration1 use the twelve snapshots reused from Validation 1. Calibration2 retains the two filenames recorded by its title-ablation output. Calibration3 uses one of the original twelve snapshots for a source-and-note ablation. The full-run directory contains the 202 held-out snapshots.

- No new sample is drawn.
- The runner discovers every PNG in the existing source/type directory structure and processes the files in sorted path order.
- Each output record retains its snapshot filename for reproducibility.
- All 202 snapshots were manually screened after extraction and confirmed legible.

The execution notebook points to:

- manifest-selected calibration images from the public dataset;
- `data/source/heldout/snapshots` for full-run images; and
- `data/source/heldout/metadata` for parent-document context.

## 4. Evidence and metadata boundaries

### 4.1 Snapshot boundary

The snapshot is the object being described. Parent-document metadata may clarify its subject, meaning, provenance, or relationship to its source document.

A proposed gap must describe:

- the snapshot itself;
- the data represented in it; or
- provenance explicitly attached to the snapshot.

Information describing only the parent document is not a snapshot-schema gap. The output does not label evidence as snapshot-, document-, or both-level. Instead, each candidate must provide its evidence and explain why the concept is snapshot metadata.

### 4.2 Reusable metadata boundary

The following are excluded:

- numerical observations and extracted values;
- OCR output and reconstructed content;
- table cells, statistical estimates, and model results;
- snapshot-specific values proposed as field names;
- visual styling without descriptive significance;
- pipeline artifacts; and
- unsupported inference or external knowledge.

An explicit methodological, uncertainty, or provenance statement may still be metadata even if the statement contains a number.

## 5. Adequate coverage

An existing field is adequate when it can preserve the information without materially distorting or losing its meaning.

For a proposed gap, the model compares:

1. a faithful representation of the evidenced information; and
2. the best representation allowed by the closest existing v1.1.1 fields.

The model then states the concrete interpretability or discoverability impairment that could follow from omission or inadequate representation. It must not assume a particular application, interface, user group, search behavior, or workflow.

## 6. Critical and possible gaps

A **critical** gap requires:

1. explicit evidence;
2. reusable snapshot metadata;
3. no adequate existing field; and
4. a concrete material impact on interpretability, discoverability, or both.

A **possible** gap must still be plausible reusable snapshot metadata with a plausible material impact, but uncertainty remains about the evidence, existing-field coverage, or materiality.

Information that is merely useful, convenient, specialized, desirable, or an additional search facet is not reported.

## 7. Structured output

Each snapshot returns:

- `coverage_assessment`: `no_critical_gap_found`, `critical_gap_found`, or `possible_gap`; and
- `critical_or_possible_gaps`: an array of candidate gaps.

There is no snapshot-level rationale. A positive coverage result and an empty candidate array are sufficient. Candidate-level explanations contain the evidence needed for human review.

Each candidate gap contains:

- a unique `gap_id`;
- `gap_status`: `critical` or `possible`;
- the missing metadata concept;
- a suggested snake-case field name;
- concise evidence;
- why the information is snapshot metadata;
- exact closest v1.1.1 fields;
- why those fields may be inadequate;
- material impact: `interpretability`, `discoverability`, or `both`;
- the concrete material consequence; and
- an uncertainty note or null.

The output does not ask the model to classify documentation, representation, or conceptual gaps. It does not ask the model to recommend accepting or implementing a field.

## 8. Calibration

Calibration0 reused the twelve snapshots used in Validation 1's calibration0 round, covering figures and tables from all three corpora. It supplied the canonical Schema v1.1.1 document, including its revision history and prior validation outcome.

Calibration1 repeats those same twelve snapshots with a model-facing Schema v1.1.1 copy that preserves the field inventory, field definitions, and substantive scope while omitting validation-history and prior-outcome language. Holding the snapshots, prompt, output model, and request settings constant isolates whether that document language affected the coverage assessments.

Calibration checks:

- adherence to the critical/possible threshold;
- exclusion of broad metadata inventories;
- exclusion of extraction values and document-only administration;
- exact use of v1.1.1 field names;
- concise, evidence-backed candidate explanations;
- internally consistent structured outputs;
- response length, latency, cache use, and cost; and
- preservation of legitimate possible gaps rather than prompt-induced suppression.

Calibration does not systematically audit `no_critical_gap_found` cases for false negatives. Calibration1 uses the same twelve snapshots rather than a new subset because it tests a single controlled change to the schema presentation.

Calibration2 is a counterfactual sensitivity test. Its pre-specified call used `oct_2023_rbsa_population_data_analysis_figure_008.png`, a simple bar chart with an explicit displayed title, and a copy of the model-facing schema from which only the `title` field was removed. A subsequent call applied the same ablation to `161_28046_table_004.png`. Both filenames are retained under `data/calibration2` because both records remain in `calibration_results2.jsonl`.

The pre-specified expected result is at least one `critical` or `possible` gap identifying the absent snapshot-title or caption concept. The proposed field name need not exactly equal `title`. A title-like gap demonstrates that the instrument can surface a known material omission; `no_critical_gap_found` would indicate inadequate sensitivity and require prompt review. Unrelated candidates do not determine whether this check passes.

Neither Calibration2 call surfaced a title-like gap, so the title ablation did not demonstrate the desired sensitivity. These outputs remain methodological controls. They are not evidence that the complete v1.1.1 schema lacks a title field and must not be included in substantive candidate counts, field adjudication, or the final schema-coverage conclusion.

Calibration3 uses `document_699863_table_004.png`. Its footer explicitly states that the data are from CIDTc, that they apply to 1987/88, and that further discussion of data construction appears in the text. The full model-facing schema produced `no_critical_gap_found` for this snapshot in Calibration1, providing the paired control. The Calibration3 schema removes only `data_source` and `interpretive_note`; references to those exact field names elsewhere in the schema are also removed or neutralized. The other 34 fields, prompts, output model, and inference settings remain unchanged. A distinct prompt-cache key labels and isolates this ablation.

The required sensitivity signal is at least one `critical` or `possible` gap identifying the missing data-source or data-provenance concept supported by “Data are from CIDTc.” A gap corresponding to `interpretive_note` is a secondary result rather than a pass requirement because the remaining note only points to discussion elsewhere without stating the construction method. The represented date remains covered by `time_period` and is not an expected gap.

Calibration3 outputs are also methodological controls. They must not be included in substantive candidate counts, field adjudication, or the final schema-coverage conclusion.

Calibration3 returned one `critical` candidate identifying the missing underlying data source, correctly distinguishing CIDTc from both `data_collection_method` and the parent document's `source_document_title`. It did not propose a redundant `time_period` gap. Calibration3 therefore met its required sensitivity criterion; the secondary interpretive-note signal was not required.

The calibration sequence is complete. No further calibration round is planned. The full run freezes the current system prompt, user prompt, Structured Output model, and inference settings, restores the complete 36-field model-facing schema, and processes all 202 held-out snapshots. The failed title ablation remains a documented limitation and the successful source ablation demonstrates sensitivity to an explicit material provenance omission.

## 9. Execution pattern

Validation 2 follows the Validation 1 execution architecture:

- GPT-5.5 with medium reasoning;
- Flex service tier;
- prompt caching;
- an 8,000-token output ceiling;
- Pydantic Structured Outputs;
- one snapshot per request;
- progress reporting with `tqdm`;
- resumable successful-result JSONL;
- a separate error JSONL;
- no automatic retry policy;
- retry by rerunning the notebook;
- retained raw response, parsed output, request settings, token usage, and elapsed time; and
- full-run outputs separate from calibration outputs.

The model and request settings remain configuration-driven. No Validation 2 API call is made until the calibration or full run is explicitly authorized.

## 10. Programmatic quality controls

Before API execution, the runner verifies:

- a non-empty schema field inventory;
- a valid model configuration;
- at least one PNG in the source/type directory structure;
- matching source/type filename structure; and
- distinct results and error paths.

After parsing, it verifies:

- unique gap identifiers and proposed names within a snapshot;
- snake-case proposed names that are not existing fields;
- exact closest-field names;
- consistency between coverage status and candidate contents; and
- resumability by successful snapshot filename.

## 11. Human adjudication

Human review examines:

- every `critical` candidate;
- every `possible` candidate; and
- technical failures that require rerunning.

There is no false-negative audit of `no_critical_gap_found` results.

For each surfaced candidate, the reviewer determines whether it is:

- adequately covered by an existing field;
- not reusable snapshot metadata;
- parent-document metadata;
- extraction content;
- insufficiently evidenced or insufficiently material;
- a documentation or representation concern; or
- a meaningful missing field.

The reviewer may additionally consider scope relevance, reusability, semantic fidelity, generalizability, parsimony, consistency, granularity, clarity, and maintainability. Candidate frequency is supporting evidence, not an acceptance rule.

No model-generated proposal changes the schema automatically.

## 12. Analysis and claim boundary

The final analysis reports:

- successful and failed calls;
- model-assessed coverage status by corpus and artifact type;
- critical and possible candidate counts;
- impact categories and closest existing fields;
- recurring candidate names and evidence; and
- human-adjudication outcomes.

Because positive assessments are not independently audited, Validation 2 does not estimate model recall or the false-negative rate. Model-assessed no-gap results are reported as model outputs rather than human-verified cases.

If no candidate warrants changing the field inventory after human review, the supported conclusion is:

> Adding the 202 held-out validation snapshots to the original 210-snapshot discovery corpus would not have changed the accepted 36-field schema inventory for the intended schema scope.

This is evidence about the tested held-out snapshots and schema scope, not a claim of universal schema saturation.
