# Data Snapshot Metadata Schema Validation 2 Report

**Date:** September 3, 2026  
**Status:** Final after human adjudication  
**Baseline:** Data Snapshot Metadata Schema v1.1.1

## Executive summary

Validation 2 tested whether Data Snapshot Metadata Schema v1.1.1 adequately
covers critical metadata needed to interpret and discover held-out data
snapshots. At the study level, it asked whether adding the 202 held-out
snapshots to the original 210-snapshot discovery corpus would have changed the
accepted 36-field schema inventory.

The validation processed all 202 snapshots successfully. The model returned
no critical gap for 197 snapshots (97.5%) and possible gaps for five snapshots
(2.5%). It returned six possible-gap records and no critical-gap records. All
six proposed field names occurred once.

Human review did not accept any proposal as a missing field. Four proposals
were rejected because they were specialized table content, extraction or
visual-encoding information, or document-reading cues without sufficient
snapshot-level interpretability or discoverability value. Two proposals
identified representation problems: associating metadata with individual
panels and preserving nested table-column relationships. These concern how
existing concepts are structured rather than whether the top-level inventory
lacks a metadata concept, and they are deferred to v1.2 design.

The supported conclusion is:

> Adding the 202 held-out validation snapshots to the original 210-snapshot
> discovery corpus would not have changed the accepted 36-field schema
> inventory for the intended schema scope.

Schema v1.1.1's field inventory is therefore stable with respect to the tested
held-out evidence. This is not a claim that future snapshots can never produce
new candidates or that the schema is universally saturated.

## 1. Goal

Validation 2 addressed the following snapshot-level question:

> Given Data Snapshot Metadata Schema v1.1.1, this snapshot, and its
> parent-document context, is there any critical or possibly critical reusable
> metadata information about the snapshot that is not adequately covered by an
> existing schema field and whose absence would materially impair
> interpretability, discoverability, or both?

The study had four objectives:

1. Test frozen Schema v1.1.1 against the 202 snapshots held out from the
   original schema-discovery corpus.
2. Identify only critical or possibly critical field-coverage gaps rather than
   repeat broad metadata discovery.
3. Submit every surfaced candidate to human review without asking the model to
   decide whether it represented a documentation, representation, or
   conceptual gap.
4. Determine whether the held-out evidence would have changed the accepted
   field inventory had it been included during initial discovery.

The [Validation 2 protocol](0.0-schema_validation2_protocol.md) pre-specified
the research question, evidence boundaries, calibration controls, human-review
procedure, and supported claim.

## 2. Methodology

### 2.1 Held-out evidence

Validation 2 reused the 202 snapshots sampled for Validation 1. These snapshots
were excluded from the original 210-snapshot schema-development sample.
Validation 2 is therefore a different confirmatory assessment of the same
held-out evidence, not a second independent held-out sample.

| Corpus | Figures | Tables | Total |
|---|---:|---:|---:|
| PRWP | 35 | 35 | 70 |
| Refugee PAD | 27 | 35 | 62 |
| UNHCR | 35 | 35 | 70 |
| **Total** | **97** | **105** | **202** |

The full-run input directory was
`data/source/heldout/snapshots`. The runner discovered every PNG
under its source/type directory structure. Reproducibility depends on the
filenames retained in [results.jsonl](../../artifacts/validation2/results.jsonl), not the order in
which the calls were made. The full-run results contain 202 unique filenames
that exactly match the 202 PNG filenames in the input directory.

All snapshots had previously been manually screened after extraction and
confirmed legible.

### 2.2 Confirmatory validation instrument

Each request supplied:

- one snapshot image;
- its source corpus and artifact type;
- associated parent-document metadata;
- the complete model-facing v1.1.1 schema; and
- the Validation 2 system and user prompts.

The parent document supplied context, but the prompt required each gap to
qualify as metadata about the snapshot rather than document administration.
The prompt did not define a particular downstream-user perspective.

The model returned:

- a snapshot-level assessment of no critical gap, possible gap, or critical
  gap; and
- an array containing only critical or possibly critical candidate gaps.

There was no snapshot-level rationale for no-gap assessments. Each positive
candidate included evidence, the missing concept, a suggested name, closest
existing fields, possible semantic loss, material impact, material
consequence, and uncertainty. The model did not decide whether a candidate was
a representation limitation and did not recommend schema acceptance.

### 2.3 History of v1.1.1 and its calibration presentation

Canonical Schema v1.1.1 was created after Validation 1's full run and human
adjudication; it did not originate from a Validation 2 calibration round.
Validation 1 found no candidate that warranted changing the 36-field v1.1
inventory, but it exposed recurring ambiguity in how several existing fields
and boundaries should be understood. A patch release was therefore
appropriate: v1.1.1 preserved all 36 fields while documenting the accepted
decisions.

The documentation-only revision clarified:

- the boundary between snapshot metadata and administrative metadata belonging
  to the linked parent document;
- that time_period describes when the represented data apply, not when the
  snapshot or document was produced or published;
- the limits of the flat data_source field for distinguishing provenance
  roles;
- the use of interpretive_note for explicit methodological, uncertainty, and
  provenance statements; and
- the treatment of variable roles and composite visualizations in v1.1.1,
  with normalized relationship-bearing representations deferred to v1.2.

Validation 2 Calibration0 supplied this canonical v1.1.1 document, including
its revision history and the statement that Validation 1 had found no
meaningful missing fields. All twelve Calibration0 snapshots returned no-gap
assessments. Although those outputs could have reflected genuine coverage, the
schema document's disclosure of the prior outcome created an avoidable
anchoring risk: the model could repeat the earlier conclusion instead of
independently assessing the snapshot.

The history-neutral **model-facing copy** of v1.1.1—not the v1.1.1 release
itself—was therefore deemed necessary after Calibration0 and introduced for
Calibration1. It removed validation-history and prior-outcome language while
preserving the complete field inventory, definitions, examples, substantive
scope, and extraction guidance. Calibration1 repeated the same twelve
snapshots so that schema presentation was the only intended change. It
returned eleven no-gap assessments and one possible component-relationship
gap. The history-neutral copy was then retained for the later controls and
frozen full run.

This separation allowed the canonical v1.1.1 document to preserve its public
revision history while preventing that history from influencing the
confirmatory model assessment.

### 2.4 Calibration and counterfactual controls

Four calibration logs were retained:

| Run | Calls | Result | Interpretation |
|---|---:|---|---|
| Calibration0 | 12 | 12 no-gap assessments | Initial confirmatory calibration |
| Calibration1 | 12 | 11 no-gap assessments; one possible component-relationship gap | Verified the model-facing schema without validation-history language |
| Calibration2 | 2 | Two no-gap assessments after removing title | Title ablation did not demonstrate the pre-specified sensitivity signal |
| Calibration3 | 1 | One critical underlying-data-source gap after removing data_source and interpretive_note | Source-and-note ablation passed its pre-specified sensitivity criterion |

Calibration2 and Calibration3 were methodological controls. Their candidate
outputs were excluded from substantive full-run counts and field
adjudication.

The failed title ablation is retained as a limitation. The successful
source-and-note ablation shows that the instrument could detect at least one
explicit, materially important provenance omission, but it does not establish
general candidate recall.

### 2.5 Execution and traceability

The [execution notebook](1.0-schema_validation2.ipynb) used GPT-5.5 with:

- medium reasoning;
- Flex service tier;
- prompt caching;
- an 8,000-token output ceiling;
- Pydantic Structured Outputs; and
- one snapshot per request.

Successful records retained the filename, corpus, artifact type,
source-document identifier, request settings, parsed output, raw response,
token usage, and elapsed time. The output was resumable by successful
snapshot filename. No automatic retry policy was used.

The [analysis notebook](2.0-schema_validation2_analysis.ipynb) checked filename
coverage, duplicate filenames, completion status, unresolved errors,
configuration consistency, resolved model identity, and agreement between
snapshot-level assessments and returned gap statuses. It also summarized
coverage, cost, calibration controls, candidate evidence, and the snapshots
requiring human review.

### 2.6 Human adjudication

Human review examined all six possible-gap records. There was no false-negative
human audit of the 197 no-gap assessments.

For each candidate, the reviewer considered:

- whether the cited information was actually evidenced;
- whether it was reusable metadata about the entire snapshot;
- whether existing fields could preserve it adequately;
- whether omission materially affected interpretability or discoverability;
- whether it generalized beyond a specialized artifact; and
- whether it represented a missing concept or a structural representation
  problem.

Candidate frequency was supporting evidence rather than an automatic
acceptance rule.

### 3.4 Candidate-gap structure

The five positive snapshots produced six possible gaps. One Refugee PAD table
produced two gaps; each of the other four snapshots produced one. The model
classified four gaps as affecting interpretability and two as affecting both
interpretability and discoverability. No candidate was classified as
discoverability-only.

The six exact proposed names were:

- data_collection_responsibility;
- data_collection_frequency;
- uncertainty_indicator;
- panel_metadata_mapping;
- visual_annotation; and
- column_group_hierarchy.

Every name occurred once. There was therefore no recurring exact-name signal
in the confirmatory run.

The closest existing field cited most often was interpretive_note, which
appeared in five gap records. Other nearby fields included
visualization_type, subject_summary, data_collection_method, time_period,
category_labels, panel_title, row_dimension, column_dimension, and
category_dimension. These references showed that most candidates concerned
the granularity or structure of an existing concept rather than a wholly
absent subject area.

## 4. Human adjudication decisions

| Proposed field | Evidence context | Decision | Rationale |
|---|---|---|---|
| data_collection_responsibility | A specialized Refugee PAD project-finance/results table named a party responsible for data collection | No new field | The concept was not common in the held-out data snapshots and occurred only as operational content in one specialized table. It does not establish a reusable top-level property of the snapshot. |
| data_collection_frequency | The same table specified when an indicator should be collected | No new field | The value is specialized monitoring-table content rather than a broadly useful snapshot metadata concept. Relevant context may be preserved in an interpretive note when necessary, but omission does not materially impair general snapshot interpretation or discovery. |
| uncertainty_indicator | An UNHCR figure displayed unlabeled error-bar-like marks | No new field; extraction or visual-encoding issue | Presence alone does not identify the type or meaning of uncertainty. A boolean indicator would provide little interpretive value, while a useful structured field would require extracting and correctly identifying the visual encoding. Unlabeled marks should not be inferred as uncertainty metadata. |
| panel_metadata_mapping | A composite UNHCR figure contained panels with different subjects, visualization types, and time periods | Representation gap deferred to v1.2 | The unit of analysis is the entire snapshot. Existing concepts can describe the overall object, but the flat schema cannot associate values with individual panels. This is a relationship and component-structure problem, not evidence for another top-level field. |
| visual_annotation | A blue oval highlighted selected categories in an UNHCR table | Exclude | The oval primarily supports a surrounding document instruction directing the reader to the encircled content. It is rare visual markup and is not required for reusable interpretation or discovery of the data snapshot. |
| column_group_hierarchy | An UNHCR table used multi-level headers that nested incident subtypes under broader violation categories | Representation gap deferred to v1.2 | Existing row, column, and category concepts capture the substantive dimensions, but the flat representation cannot preserve their hierarchy. A future structured table model should represent nested groups and levels; this does not justify another top-level v1.1.1 field. |

## 5. Main findings

### 5.1 The accepted field inventory is stable

No critical gap was returned, and none of the six possible gaps survived human
review as a missing field. Had the 202 held-out snapshots been included in the
initial discovery phase, they could have produced additional proposed names,
but the evidence does not support adding any of those names to the accepted
inventory.

The appropriate stability claim concerns accepted fields, not candidate
generation:

> Adding the 202 held-out validation snapshots to the original 210-snapshot
> discovery corpus would not have changed the accepted 36-field schema
> inventory for the intended schema scope.

### 5.2 Rare semantic distinctions do not automatically require fields

The model surfaced valid differences, including collection responsibility,
collection frequency, uncertainty marks, and visual annotations. Human review
found that these distinctions were specialized, extraction-oriented, weakly
specified, or not materially useful for snapshot-level interpretation and
discovery.

Rarity was not used as the sole rejection rule. The decisions also considered
whether the evidence described the snapshot as a whole, whether an operational
metadata value could be populated reliably, and whether omission caused a
material interpretability or discoverability problem.

### 5.3 The remaining issues concern representation

Panel metadata mapping and column-group hierarchy expose the limitations of a
flat field inventory. In both cases, the relevant concepts already exist:
panels have types and titles, and tables have row, column, and category
dimensions. What is missing is a mechanism for preserving relationships among
those values.

Adding more flat fields would treat a structural problem as a vocabulary
problem. These findings belong in the v1.2 representation backlog.

### 5.4 Human review remains essential

The model provided a small, evidence-bearing review set, but it could not
decide architectural fit, generalizability, representational granularity, or
the intended unit of analysis. Human review determined that:

- operational table cells were not necessarily snapshot metadata;
- unlabeled visual encodings could not support a meaningful field;
- document-reading markup was not a discovery requirement; and
- structural relationships should not become isolated top-level fields.

This is consistent with the intended human-in-the-loop design: the model
screens broadly enough to expose plausible omissions, while human reviewers
decide whether they warrant schema change.

## 6. Relationship to Validation 1

Validation 1 performed broad residual discovery over the held-out corpus. It
generated thousands of observations and hundreds of candidate proposals,
which human review resolved without accepting a consequential new v1.1 field.
Validation 2 asked a narrower question of the same evidence: whether each
snapshot contained any critical or possibly critical information not
adequately covered by v1.1.1.

The two exercises provide complementary evidence:

- Validation 1 showed that broad candidate generation did not reveal a
  consequential missing top-level concept after complete review.
- Validation 2 showed that a confirmatory, materiality-focused screen produced
  only six possible gaps, none of which warranted changing the field
  inventory.

Because the same held-out snapshots were used, these are complementary
assessments rather than independent statistical replications.

## 7. Takeaways for v1.2

No v1.2 schema is implemented in the repository at the time of this report.
The findings identify design requirements rather than confirming that v1.2
already handles them.

### 7.1 Composite and multi-panel snapshots

The v1.2 representation should be able to associate existing metadata with
individual components while retaining the entire snapshot as the cataloged
unit. A component may need its own visualization type, title, subject, time
period, or other relevant values. Component count should remain derivable from
the structured component collection rather than become an independently
authored field.

### 7.2 Nested table structure

The v1.2 representation should consider hierarchical row and column groups,
including:

- multiple header levels;
- parent-child category relationships;
- labels attached to a particular hierarchy level; and
- explicit association between a dimension and its displayed groups.

This should normalize relationships among existing dimension and category
concepts rather than add column_group_hierarchy as a standalone top-level
field.

### 7.3 Items not added to the v1.2 gap backlog

The following Validation 2 proposals do not require dedicated v1.2 work:

- data-collection responsibility and frequency from specialized operational
  tables;
- an unlabeled uncertainty indicator;
- rare visual annotation used as a document-reading cue.

Future evidence may still motivate different decisions, but these candidates
do not establish current schema requirements.

## 8. Limitations and claim boundary

- Validation 2 evaluated 202 snapshots from three institutional corpora. The
  result may not generalize to every document domain or visualization
  practice.
- Validation 2 reused the Validation 1 held-out corpus. It is not an
  independent second sample.
- Twelve snapshots were reused during prompt calibration, leaving 190
  snapshots untouched by Validation 2 prompt calibration.
- The assessment used one model snapshot and one final prompt configuration.
  Another model or prompt may produce different candidates.
- There was no human false-negative review of the 197 no-gap assessments.
  Validation 2 therefore does not estimate candidate recall or the
  false-negative rate.
- The title ablation did not surface the intentionally removed concept. This
  demonstrates a sensitivity limitation even though the source-and-note
  ablation succeeded.
- Candidate rarity supports but does not determine rejection. A rare concept
  could still warrant a field if it were sufficiently material,
  generalizable, and operationally representable.
- Stability means that no consequential top-level field was accepted from the
  tested held-out evidence. It does not guarantee that every possible future
  snapshot will fit v1.1.1 without ambiguity.

## 9. Conclusion

Validation 2 processed all 202 held-out snapshots without technical failure
and returned six possible gaps across five snapshots. Complete human review
accepted no candidate as a missing metadata field. Four candidates were
rejected or excluded, while panel metadata mapping and nested column hierarchy
were classified as representation problems for future v1.2 design.

The results answer the study-level research question in the negative: adding
the tested 202 snapshots to the original discovery corpus would not have
changed the accepted 36-field inventory. Data Snapshot Metadata Schema
v1.1.1's field inventory is stable for the intended scope with respect to this
held-out evidence.

The remaining work is not additional broad field discovery. It is the future
design of structured representations for relationships already exposed by the
existing concepts, together with continued documentation of the schema's
scope and human decision record.
