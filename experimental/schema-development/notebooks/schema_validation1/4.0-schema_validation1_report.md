# Data Snapshot Metadata Schema Validation 1 Report

**Date:** August 28, 2026  
**Status:** Final after human adjudication

## Executive summary

This exercise tested whether Data Snapshot Metadata Schema v1.1 remained adequate when applied to a new set of data snapshots that had not been used to engineer the schema. The practical question was whether the original 210-snapshot development sample was sufficient to establish a stable metadata core for the intended downstream application.

The validation processed 202 snapshots from three corpora and produced 2,876 evidence-bearing observations. The model classified 2,275 observations (79.1%) as covered by v1.1 and proposed 578 candidate fields from weak-fit or no-fit observations. Human review consolidated obvious naming variants into 14 provisional review families, examined the 60 candidate rows outside those families, and separately checked all 23 uncertain or out-of-scope observations.

No candidate warranted a meaningful addition to or change in Schema v1.1. Proposed concepts were either:

- extraction values rather than snapshot metadata;
- adequately represented by existing fields;
- valid concepts intentionally excluded by the application architecture or use case; or
- representation problems better addressed through v1.2 normalization than through new flat fields.

The result supports the conclusion that the original 210 snapshots were sufficient to establish the common metadata-field core for the intended application. This is a use-case-specific stability result, not a claim of universal schema saturation.

## 1. Goal

The validation had four objectives:

1. Test frozen Schema v1.1 against new snapshots excluded from the original schema-engineering sample.
2. Identify recurring metadata concepts that were absent from or poorly represented by v1.1.
3. Distinguish true schema gaps from extraction outputs, naming variants, source-document metadata, and concepts without sufficient downstream value.
4. Determine whether additional broad discovery sampling was likely to produce consequential new top-level fields.

The frozen baseline was the canonical [Data Snapshot Metadata Schema v1.1](../../schemas/Data%20Snapshot%20Metadata%20Schema%20v1.1.md). The validation model could propose candidates, but field acceptance remained a human decision.

## 2. Methodology

### 2.1 Held-out sampling

The [study-manifest notebook](0.0-study_manifests.ipynb) verifies the realized sample recorded in `data/manifests/heldout_snapshots.csv`. The original selection excluded snapshots used in the 210-snapshot development sample, then randomly selected up to 35 figures and 35 tables from each corpus. Only 27 eligible Refugee PAD figures remained after the development sample was removed.

| Corpus | Figures | Tables | Total |
|---|---:|---:|---:|
| PRWP | 35 | 35 | 70 |
| Refugee PAD | 27 | 35 | 62 |
| UNHCR | 35 | 35 | 70 |
| **Total** | **97** | **105** | **202** |

All 202 snapshots were held out from schema engineering. Twelve were subsequently used to calibrate the validation instrument, leaving 190 snapshots untouched during prompt calibration.

The sampling notebook used `random.sample` without a fixed seed. The realized sample was preserved in the validation data directory, but rerunning the sampling procedure from the source corpus would not necessarily reproduce the same draw. Future validation runs should set a seed and save an explicit sample manifest.

### 2.2 Validation instrument

Each request supplied:

- one snapshot image;
- its source corpus and artifact type;
- associated source-document metadata;
- the complete frozen v1.1 schema; and
- the [schema-validation instructions](../../src/schema_development/validation1/prompts/system.md).

The model returned a Pydantic Structured Output containing:

- one evidence-bearing observation per reusable metadata concept;
- the closest existing schema fields;
- a fit classification (`covered`, `weak_fit`, `no_fit`, `uncertain`, or `out_of_scope`); and
- candidate new fields supported only by weak-fit or no-fit observations.

The prompt intentionally supported broad discovery. It did not encode every downstream architectural or product decision. This allowed the LLM to surface plausible distinctions while preserving human responsibility for determining whether those distinctions belonged in the operational schema.

### 2.3 Calibration

The validation procedure was calibrated in three logged rounds:

1. An initial 12-snapshot run exposed excessive verbosity, unnecessary inventory-style observations, and high output cost.
2. A revised 12-snapshot run tested a more focused prompt together with Flex processing and prompt caching.
3. A final six-snapshot check verified that the prompt still allowed valid time, provenance, and data-source candidates instead of suppressing them prematurely.

The final prompt emphasized explicit evidence, concise rationales, genuine boundary questions, exact v1.1 definitions, and candidates only where an in-scope concept had weak or no fit. It still left operational usefulness and field acceptance to human adjudication.

### 2.4 Execution and traceability

The [execution notebook](2.0-schema_validation1.ipynb) called GPT-5.5 with medium reasoning, Flex service tier, prompt caching, and an 8,000-token output limit. The pipeline:

- discovered snapshots from the source/type directory structure;
- matched source-document metadata by document identifier;
- displayed progress with `tqdm`;
- wrote successful calls to resumable JSONL checkpoints;
- retained raw responses, parsed outputs, token usage, and request settings; and
- allowed incomplete items to be retried by rerunning the notebook.

No automatic retry policy was used. This kept execution behavior visible and notebook-driven.

### 2.5 Analysis and human adjudication

The [analysis notebook](3.0-schema_validation1_analysis.ipynb) summarized cost, coverage, fit status, candidate frequency, corpus differences, and supporting evidence. The [observation viewer](3.1-schema_validation1_viewer.ipynb) flattened the Structured Output into one row per observation.

Candidate names were not normalized by the LLM. Fourteen provisional `review_family` groups were created manually as an analysis aid to consolidate obvious semantic aliases. These groups covered 518 of the 578 candidate rows. Human review then examined:

- all 14 candidate families;
- the remaining 60 candidates not assigned to a family; and
- all 23 boundary-quality rows: 20 `uncertain` and three `out_of_scope`.

The family grouping was not part of the prompt and was not treated as a model output or an accepted schema layer.

### 3.3 Candidate structure

The model generated 578 candidate proposals using 101 exact names; 70 exact names occurred only once.

| Evidence level | Proposals | Affected snapshots | Exact names | No-fit supports |
|---|---:|---:|---:|---:|
| Document | 452 | 193 | 19 | 369 |

Document-level candidates accounted for 78.2% of proposals. Four manually consolidated source-document families—retrieval, identity/type, publication date, and attribution—accounted for 443 candidate rows. This concentration reflected the prompt's broad treatment of source-document metadata and the metadata exposed by each corpus, not an automatic finding that those fields belonged in the snapshot schema.

Snapshot-level proposals were much narrower and heavily long-tailed. Most were weak fits or isolated names rather than recurring unambiguous omissions.

## 4. Human adjudication decisions

| Candidate area | Decision | Rationale |
|---|---|---|
| Source-document URL, locator, identifier, type, publication date, and attribution | Exclude from snapshot schema | The downstream application links each snapshot to a source document with its own metadata. Duplicating document administration in the snapshot record is unnecessary. |
| Snapshot artifact date | No dedicated v1.1 field | Data dates belong in `time_period`. A complete footer or provenance statement can be retained in `interpretive_note`; source-document publication metadata remains on the linked document. |
| Snapshot artifact creator or map maker | No new v1.1 field | The concept is valid, but v1.2 should consider a role-bearing provenance or `data_source` representation rather than a separate flat creator field. |
| Cartographic scale and coordinates | Exclude by use case | These are genuine map-description concepts but do not materially support the project's cataloging, discovery, or knowledge-graph goals. |
| Analytical variable and axis roles | Defer to v1.2 representation | Existing fields retain variables and dimensions, while v1.2 normalization can preserve roles such as outcome, predictor, control, x-axis, and y-axis without proliferating flat fields. |
| Classification systems, levels, rules, and hierarchies | No v1.1 field | A field such as `classification_system: HS` was judged too specialized for the domain-general schema based on the available evidence. Explicit statements can remain in category fields or `interpretive_note`. |
| Composite visualization structure | Defer to v1.2 representation | The core concept is already present in `visualization_type` and `panel_title`. v1.2 should represent individual components and their types more cleanly. |
| `panel_count` | Reject as a canonical field | It has limited independent discovery value and is derivable from a normalized list of visualization components. |
| Data-collection timing and responsibility | Treat as extraction values | The evidence came from operational table cells rather than reusable snapshot metadata. |
| Sample size | Use existing fields and improve examples | An explicit sample size can be retained in `title` or `interpretive_note`. A dedicated field is not justified by the intended retrieval use case. |
| Uncertainty representation | Use `interpretive_note` when explicit | Text explaining confidence bands or standard errors is an interpretive note. Unlabeled whisker-like marks should remain uncertain rather than being inferred as uncertainty metadata. |
| Reference event or context | Use existing fields | `subject_summary`, `comparison_group`, `intervention_type`, temporal fields, and category fields can preserve the substantive content. More explicit relationships are a normalization concern. |
| Remaining 60 candidate rows | No additions | Review found extraction values, concepts covered by existing fields, or specialized concepts without sufficient use-case value, such as log transformation. |
| Twenty uncertain and three out-of-scope rows | No additions | These were evidence ambiguities or correctly excluded extraction/statistical contents, not recurring missing-field evidence. |

No model-generated candidate was accepted as a new v1.1 field.

## 5. Main findings

### 5.1 The common snapshot-content schema is stable

Most observations fit existing fields, and the snapshot-level candidate set did not contain a recurring, operationally important top-level concept that survived human review. Additional broad sampling is therefore unlikely to be more informative than improving representation and documentation in v1.2.

### 5.2 Semantic difference is not sufficient for field acceptance

The LLM correctly identified several distinctions not represented losslessly by flat v1.1 fields: artifact dates versus data periods, data origin versus map creation, dependent versus explanatory variables, and primary versus component visualization types. Human reviewers nevertheless rejected or deferred them because a metadata schema must also reflect application architecture, expected retrieval behavior, generalizability, and maintenance cost.

### 5.3 Source-document metadata dominated automated gap discovery

The model repeatedly proposed document URLs, identifiers, dates, types, and creators because the prompt allowed document metadata that supported retrieval or provenance. These proposals were internally reasonable but incompatible with the application's linked-document architecture. Their prevalence demonstrates that candidate frequency alone is not evidence for field acceptance.

### 5.4 Human normalization and adjudication were indispensable

The model generated semantically related names such as `source_document_url` and `source_document_locator`, or `snapshot_creator`, `snapshot_producer`, and `snapshot_attribution`. Manual review families reduced this naming variation without pretending the model had produced a higher-level taxonomy.

More importantly, human reviewers applied criteria unavailable from the schema text alone:

- whether metadata already existed elsewhere in the application;
- whether end users would realistically search or filter by the field;
- whether a concept generalized beyond one artifact class or corpus;
- whether the value was extraction output rather than metadata; and
- whether the issue required a new concept or only a better representation.

This separation between broad LLM-assisted discovery and human schema acceptance is direct evidence for the value of the human-in-the-loop methodology.

## 6. Learnings

1. **Keep discovery broader than acceptance.** Encoding every product decision in the LLM prompt would reduce review volume, but it would also hide plausible concepts and weaken the evidence for human adjudication. The prompt should enforce fundamental evidence and metadata boundaries while leaving application-specific value judgments to experts.

2. **Define the application architecture during adjudication.** The source-document proposals were resolved only after applying the rule that document metadata resides on linked document records.

3. **Separate conceptual gaps from representation gaps.** Analytical roles and composite visualization structure revealed information that a flat schema represents awkwardly. Adding more flat fields would treat a structural problem as a vocabulary problem.

4. **Operational-value language needs human scrutiny.** The model could invent plausible benefits such as filtering by map scale, sample size, panel count, or variable transformation. Plausibility did not establish relevance to this project's users.

5. **Retain positive and boundary evidence.** Covered, uncertain, and out-of-scope observations made the assessment auditable and helped distinguish true omissions from ambiguity or extraction content.

6. **Calibration can control cost without suppressing discovery.** Concise evidence and rationale requirements reduced output volume. Flex processing and prompt caching further lowered cost while preserving structured results.

7. **Future sampling should be reproducible by construction.** Set a fixed random seed and save the selected filenames, source-document identifiers, eligibility counts, and exclusions in a manifest.

## 7. Takeaways for v1.2

v1.2 should improve how existing concepts are represented rather than expanding the top-level field inventory substantially.

For this report, a **documentation gap** means that the intended scope or use of an existing field is not sufficiently explicit in the schema definition, examples, or extraction guidance. A **representation gap** means that the relevant concept is present, but the flat v1.1 structure cannot preserve an important role, relationship, component, or cardinality without distortion.

### 7.1 Complete documentation-gap inventory

| v1.1 field or scope area | Candidate fields or families that exposed the gap | Documentation change for v1.2 |
|---|---|---|
| `time_period` | `snapshot_date`, `snapshot_creation_date`, `snapshot_production_date`; source-document publication-date candidates | State explicitly that `time_period` describes the period represented by the data, not the date on which the snapshot artifact or parent document was created, issued, published, revised, or retrieved. A source-document date remains on the linked document. A complete footer statement containing an artifact date may be retained in `interpretive_note`, but no dedicated artifact-date field is currently justified. |
| `interpretive_note` | `sample_size`, `uncertainty_representation`, artifact-date/footer observations | Expand the definition or examples to show that explicitly stated methodological and provenance notes may include sample-size statements, explanations of confidence intervals, standard errors or uncertainty bands, and complete footer statements relevant to interpretation or traceability. This does not create structured `sample_size`, uncertainty, or artifact-date fields. |
| `data_source` | `snapshot_creator`, `snapshot_producer`, `snapshot_contributor`, `snapshot_attribution` | Clarify whether `data_source` remains limited to the origin of represented data or becomes an umbrella for credited provenance agents. If v1.2 adopts the latter interpretation, document allowed roles such as data source, publication source, map maker, snapshot producer, preparer, and contributor. The field name may need reconsideration if it represents agents that are not literally data sources. |
| Parent-document boundary, including `source_document_title` and the snapshot-document relationship | Retrieval: `source_document_url`, `source_document_locator`; identity/type: `source_document_identifier`, `source_document_type`; dates: `source_document_publication_date`, `source_document_date`; attribution: `source_document_creator`, `source_document_contributor`, `source_document_author`, `source_document_producer`, `source_document_organization`, `source_document_attribution` | State that parent-document administrative metadata is resolved through the application's snapshot-document link and is not duplicated as new snapshot metadata fields. Clarify which document-context values, if any, may still populate existing snapshot fields and distinguish contextual evidence from metadata copied from the document record. |
| `visualization_type` and `panel_title` | `visualization_composition`, `visualization_component_type`, `visualization_components`, `embedded_visualization_type`, `panel_count` | Update the definitions and examples after the v1.2 component model is chosen. Explain how to encode single visualizations, multi-panel figures, mixed composites, repeated visualization types, embedded or inset visualizations, and untitled panels. State that `panel_count` is derived rather than independently authored. |
| `variable_name`, `category_dimension`, `category_labels`, `row_dimension`, `column_dimension`, and `analysis_method` | `axis_variable`, `axis_assignment`, `dependent_variable`, `outcome_variable`, `explanatory_variable`, `model_variable_role` | Explain how a represented variable's name differs from its structural or analytical role. Document the normalized v1.2 mechanism for roles such as outcome, predictor, control, row dimension, column dimension, x-axis, and y-axis instead of directing extractors to create new flat fields. |

These documentation changes are intended to make accepted scope decisions and normalized representations understandable to extractors and downstream consumers. They should not suppress broad candidate discovery during future validation; human adjudication remains responsible for applying application-specific value judgments.

### 7.2 Complete representation-gap inventory

#### 7.2.1 Provenance agents and roles

**Existing v1.1 field:** `data_source`  
**Candidate family:** `snapshot_creator`, `snapshot_producer`, `snapshot_contributor`, `snapshot_attribution`

v1.1 can record the source from which represented data originate, but it cannot distinguish that source from a credited map maker, snapshot producer, preparer, or contributor. v1.2 should use a role-bearing collection, for example:

```json
{
  "data_source": [
    {"name": "Some database", "role": "data source"},
    {"name": "Map Design Unit", "role": "map maker"}
  ]
}
```

The team should decide whether `data_source` is the correct umbrella name or whether a broader provenance or attribution structure would be clearer. Parent-document administrative metadata should remain accessible through the snapshot-document relationship rather than being duplicated.

#### 7.2.2 Composite visualization components

**Existing v1.1 fields:** `visualization_type`, `panel_title`  
**Candidate family:** `visualization_composition`, `visualization_component_type`, `visualization_components`, `embedded_visualization_type`; related candidates `panel_count` and `locator_inset`

Represent individual panels or components explicitly, including their visualization type and optional panel title. `panel_count` should be derived from the component list rather than stored independently. Repeating types in a bare `visualization_type` list can encode count implicitly, but component objects better preserve identity and relationships.

An illustrative direction is:

```json
{
  "visualization_components": [
    {"visualization_type": "line_graph", "panel_title": "Panel A"},
    {"visualization_type": "line_graph", "panel_title": "Panel B"},
    {"visualization_type": "map", "role": "locator inset"}
  ]
}
```

This representation preserves repeated types and embedded visualizations while making `panel_count` a deterministic derived value.

#### 7.2.3 Analytical and structural variable roles

**Existing v1.1 fields:** `variable_name`, `category_dimension`, `category_labels`, `row_dimension`, `column_dimension`, `analysis_method`  
**Candidate family:** `axis_variable`, `axis_assignment`, `dependent_variable`, `outcome_variable`, `explanatory_variable`, `model_variable_role`

Allow represented variables to carry roles such as outcome, predictor, control, row dimension, column dimension, x-axis, or y-axis. This should normalize the relationship between existing concepts rather than create separate top-level fields for each role.

An illustrative direction is:

```json
{
  "variables": [
    {"name": "Poverty rate", "role": "outcome", "axis": "y"},
    {"name": "GDP per capita", "role": "predictor", "axis": "x"}
  ]
}
```

The final v1.2 design may retain the existing field names, but it must preserve the relationship between each variable and its role instead of relying on parallel unlinked lists.

### 7.3 Items reviewed but not classified as v1.2 gaps

The following proposals were explicitly reviewed and are not part of the documentation- or representation-gap backlog:

- **Cartographic scale and coordinates:** `map_scale`, `cartographic_scale`, `map_scale_unit`, `coordinate_grid`, and `coordinate_extent` were excluded by the intended use case.
- **Classification semantics:** `classification_system`, `classification_level`, `classification_rule`, and `category_hierarchy` did not have sufficient cross-domain value to justify dedicated fields.
- **Data-collection timing and responsibility:** `data_collection_frequency`, `data_collection_schedule`, `data_collection_responsibility`, and `data_collection_responsible_party` were extraction values from operational table cells.
- **Reference event or context:** `reference_event`, `temporal_reference_event`, and `event_context` were judged representable through existing subject, comparison, intervention, temporal, and category fields or treated as extraction values.
- **Specialized analytical details:** candidates such as `variable_transformation` were excluded because they did not provide sufficient discovery value for this application.
- **Panel count:** `panel_count` is not an independent metadata field; it belongs only as a value derived from the composite-component representation described above.

### 7.4 Preserve the human decision record

v1.2 documentation should distinguish:

- concepts covered by existing fields;
- concepts excluded by the application architecture;
- extraction outputs;
- low-value specialized concepts; and
- representation gaps deferred from v1.1.

This makes future validation cumulative rather than requiring the same decisions to be reconstructed.

## 8. Limitations and claim boundary

- The run evaluated three institutional corpora and may not represent every document domain or visualization practice.
- Twelve of the 202 snapshots were used to calibrate the validation prompt, although none was used to engineer v1.1. The untouched validation subset therefore contains 190 snapshots.
- The assessment used one model and one final prompt configuration. Candidate recall and phrasing may vary with another model or prompt.
- Candidate counts are correlated within shared document templates and source metadata; repeated proposals are not independent votes.
- Human decisions are intentionally use-case dependent. Another application—for example, a cartographic archive or survey registry—could reasonably accept fields rejected here.
- Stability means that no consequential top-level field was accepted from this held-out exercise. It does not mean that every possible future data snapshot is guaranteed to fit v1.1 without ambiguity.

## 9. Conclusion

The held-out validation found many plausible metadata distinctions but no field that justified changing Data Snapshot Metadata Schema v1.1 after complete human review. The original 210-snapshot development sample therefore appears sufficient for the intended schema scope and downstream application.

The exercise also demonstrated why LLM-assisted discovery cannot replace schema engineering judgment. The model was effective at generating evidence-bearing candidates and exposing semantic distinctions, while humans determined architectural fit, operational value, generalizability, and the appropriate boundary between vocabulary and representation. The principal work for v1.2 is consequently normalization and clarification, not another expansion of the top-level metadata-field set.
