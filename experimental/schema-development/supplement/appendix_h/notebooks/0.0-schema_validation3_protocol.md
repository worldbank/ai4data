# Data Snapshot Metadata Schema Validation 3 Protocol

> `Validation 3` is the historical internal name for the paper's Appendix H
> post-study comparison.

**Schema under evaluation:** Data Snapshot Metadata Schema v1.2

**Reference design:** Schema Validation Exercise 2

**Substantive corpus:** The same 202 snapshot filenames processed by Validation 2

## 1. Objective

Validation 3 repeats the Validation 2 coverage exercise with Schema v1.2. The
measurement instrument remains the same except for changes strictly required to
supply and reference the nested v1.2 JSON Schema.

The core question is:

> Given Data Snapshot Metadata Schema v1.2, this snapshot, and its
> parent-document context, is there any critical or possibly critical reusable
> metadata information about the snapshot that is not adequately covered by an
> existing field and whose absence would materially impair interpretability,
> discoverability, or both?

At the study level, the exercise asks whether the tested corpus surfaces a
candidate that warrants changing the accepted v1.2 metadata field inventory.
It is not a general search for representation improvements.

## 2. Instrument parity with Validation 2

The following remain fixed relative to Validation 2:

- the 202 substantive snapshot filenames and their parent-document metadata;
- one snapshot per request;
- the coverage-focused system prompt and candidate thresholds;
- the requirement to express each candidate as a broadly reusable proposed
  field;
- the candidate-only human-review design;
- GPT-5.5, medium reasoning, Flex processing, 8,000 output tokens, prompt
  caching, timeout, and disabled automatic retries; and
- resumable success JSONL, separate error JSONL, raw responses, usage, and
  elapsed-time recording.

Only the following adaptations are permitted:

1. The evaluated v1.1.1 Markdown schema is replaced by JSON Schema serialized
   from canonical `DataSnapshotMetadata` v1.2 at run start.
2. `closest_schema_fields` becomes `closest_schema_paths`, allowing exact
   nested paths such as `variables[].unit`.
3. The provenance control removes the v1.2 root fields `provenance` and
   `interpretive_notes` from a local schema copy.

The prompt must not enumerate structural candidate types, emphasize relational
loss beyond the Validation 2 wording, describe known representation findings,
or disclose prior validation outcomes. There is no fingerprint, manifest,
`prepare_run()`, or run-management layer.

## 3. Inputs and boundary

Each request receives:

- the complete generated v1.2 JSON Schema, or the local ablated copy used only
  for the provenance control;
- one PNG snapshot;
- source corpus and artifact type; and
- the matching parent-document metadata object.

The snapshot is the object under validation. Parent metadata is contextual and
does not become snapshot metadata unless the supplied evidence establishes a
snapshot-specific role.

Extracted observations, OCR reconstruction, analytical results, styling without
descriptive significance, implementation artifacts, and unsupported inference
remain outside scope. Explicit methodological, uncertainty, or provenance notes
may qualify when they describe the represented data.

## 4. Critical and possible gaps

A critical candidate requires explicit evidence, reusable snapshot relevance,
no adequate existing v1.2 field, and a concrete material interpretability or
discoverability consequence.

A possible candidate must still be plausible reusable snapshot metadata with a
plausible material consequence, but may retain uncertainty about evidence,
existing-field coverage, or materiality.

Information that is merely useful, convenient, specialized, desirable, or an
additional search facet does not qualify.

## 5. Structured Output contract

`SchemaValidationResult` contains:

- `coverage_assessment`: `no_critical_gap_found`, `possible_gap`, or
  `critical_gap_found`; and
- `critical_or_possible_gaps`: an array of `CandidateGap` records.

Each `CandidateGap` contains:

- `gap_id`;
- `gap_status`;
- `missing_metadata_concept`;
- `proposed_field_name`;
- `evidence`;
- `why_snapshot_metadata`;
- `closest_schema_paths`;
- `why_existing_fields_may_be_insufficient`;
- `material_impact`;
- `material_consequence`; and
- `uncertainty_note`.

This is the Validation 2 contract with only the closest-location field adapted
to nested paths. It does not contain a separate faithful-representation field
or invite candidates that are only structural concerns.

Output consistency requires an empty candidate array for a no-gap result, at
least one critical candidate for a critical result, and only possible
candidates for a possible result. Gap identifiers and proposed field names must
be unique within a snapshot. Proposed names must be new snake-case field names.
Every reported closest path must occur in the supplied generated schema.

## 6. Calibration

Calibration evidence is methodological and excluded from substantive counts.

### Calibration0: complete schema

Run the complete v1.2 schema on the existing balanced 12-snapshot Calibration0
set. Confirm input resolution, prompt parity, exact nested paths, output
consistency, and adherence to the field-proposal threshold.

### Calibration1: provenance sensitivity control

Run `document_699863_table_004.png` with a local generated schema copy that
removes only `provenance` and `interpretive_notes`. The pre-specified pass signal
is at least one critical or possible candidate identifying the displayed CIDTc
data-source or provenance concept. The paired complete-schema Calibration0
assessment is the baseline.

Review both calibration rounds before freezing the instrument. Add another
numbered calibration only if a concrete instrument defect requires it. A new
round may use additional samples outside Validation 1 and 2, but requires
explicit permission before adding or copying ignored or untracked data.

## 7. Substantive execution

After calibration approval, freeze the complete schema, prompts, response
contract, and request configuration. Run the same 202 filenames processed by
Validation 2. Use separate result and error files for every calibration round
and the full run. The user executes every live API notebook cell.

Preflight must establish:

- exactly 12 Calibration0 filenames for the first round;
- an exact 202-filename match with Validation 2 for the substantive run;
- one resolvable parent-metadata file per selected snapshot;
- distinct success and error paths;
- canonical schema serialization and valid nested-path discovery; and
- local provenance ablation that cannot mutate the canonical model.

There are no automatic retries. Successful filenames are skipped on rerun;
failed filenames remain eligible for a later manual rerun.

## 8. Human review and analysis

Human review examines every critical and possible candidate and any technical
failure requiring rerun. No-gap cases are not independently audited.

For each candidate, determine whether it is adequately covered, outside the
snapshot boundary, extraction content, insufficiently evidenced or material, a
documentation or representation concern, or a meaningful missing field. No
model proposal changes the schema automatically.

The final analysis reports execution integrity, model assessment counts by
corpus and artifact type, candidate names and closest paths, calibration
controls, API usage and cost, and human-adjudication outcomes. Calibration is
excluded from substantive counts.

## 9. Claim boundary

The conclusion is limited to current Schema v1.2 and the tested 202-snapshot
corpus. The design does not estimate model recall or a false-negative rate and
cannot establish universal completeness.

Because v1.2 includes both substantive schema changes and a Pydantic-generated
representation, the exercise must not claim that implementation format alone
caused or prevented a result. Instrument parity permits a descriptive
Validation 2 comparison; it does not create a causal Markdown-versus-Pydantic
experiment.
