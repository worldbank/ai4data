# Data Snapshot Metadata Schema Validation 3 Report

> `Validation 3` is the historical internal name for the paper's Appendix H
> post-study comparison.

**Date:** September 8, 2026  
**Status:** Final after human adjudication  
**Schema evaluated:** Data Snapshot Metadata Schema v1.2 before the
post-validation multi-axis amendment  
**Reference design:** Schema Validation Exercise 2

## Executive summary

Validation 3 repeated the Validation 2 field-coverage exercise using Data
Snapshot Metadata Schema v1.2. The substantive corpus, parent-document
metadata, one-snapshot-per-request design, model, reasoning effort, service
tier, output limit, and candidate threshold were retained. The necessary
changes were the replacement of the v1.1.1 Markdown schema with JSON Schema
generated from the canonical Pydantic model and the use of exact nested schema
paths in candidate responses.

All 202 substantive snapshots completed successfully with no unresolved
errors. The model returned no critical gap for 171 snapshots (84.7%), possible
gaps for 28 snapshots (13.9%), and critical gaps for three snapshots (1.5%).
The 31 positive snapshots produced 36 candidate records: 33 possible and three
critical.

Human adjudication accepted none of the proposed names as a new standalone
metadata concept or top-level field. Most candidates requested extraction of
internal table, chart, map, or diagram structure; lacked sufficient
generalizability or materiality; or could be represented adequately using
existing v1.2 fields at the snapshot level.

One candidate identified a valid representation gap: variables in a dual-axis
graph could be assigned to a general y-axis role, but the evaluated schema
could not distinguish the particular axis used by each variable. This finding
did not add a new metadata concept. It warranted a nested structural
improvement to the existing variables representation. After the run, v1.2 was
amended with variables[].axis_assignments, which records the x or y dimension,
plot side, and same-side position of a distinct axis.

Two panel_metadata candidates reproduced the panel-association issue already
identified in Validation 2. They therefore do not constitute a new Validation
3 finding. The current design keeps panel_titles ordered and
visualization_types at snapshot level. A possible minimal panel descriptor
containing only title and visualization type remains pending discussion with
Aivin.

The supported conclusion is:

> Validation 3 did not identify a new metadata concept that warrants extending
> the accepted v1.2 field inventory. It identified one actionable
> representation limitation within variables: explicit assignment to distinct
> axes in a multi-axis graph. The tested field inventory is otherwise stable
> for the intended snapshot-level scope.

This conclusion is limited to the tested corpus and model-facing instrument.
The exercise does not establish universal completeness, estimate model recall,
or isolate an effect of Markdown versus Pydantic.

## 1. Goal

Validation 3 addressed the following snapshot-level question:

> Given Data Snapshot Metadata Schema v1.2, this snapshot, and its
> parent-document context, is there any critical or possibly critical reusable
> metadata information about the snapshot that is not adequately covered by an
> existing field and whose absence would materially impair interpretability,
> discoverability, or both?

At study level, the exercise asked whether the tested corpus surfaced a
candidate that warranted changing the accepted v1.2 metadata field inventory.
It was not intended as broad metadata discovery or an unrestricted search for
ways to reproduce internal snapshot content.

The
[Validation 3 protocol](0.0-schema_validation3_protocol.md)
pre-specified the instrument-parity requirement, evidence boundary,
calibration controls, candidate-only review design, and supported claim.

snapshots were originally held out from the schema-discovery corpus. Validation
3 is therefore a repeated assessment of the same evidence under v1.2, not an
independent held-out sample.

The runner discovered every PNG under the Validation 1 snapshot directory.
The 202 result filenames were unique and exactly matched both the available
input filenames and the Validation 2 result filenames.

### 2.2 Confirmatory instrument

Each request supplied:

- one snapshot image;
- its corpus and artifact type;
- matching parent-document metadata;
- complete JSON Schema serialized from canonical DataSnapshotMetadata v1.2;
  and
- the history-neutral Validation 3 system and user prompts.

The response contract was the Validation 2 contract with one structural
adaptation: closest_schema_fields became closest_schema_paths so the model
could cite exact nested locations such as variables[].unit.

The following remained fixed relative to Validation 2:

- GPT-5.5 with medium reasoning;
- Flex processing;
- an 8,000-token output ceiling;
- prompt caching;
- one snapshot per request;
- candidate thresholds and materiality requirements;
- Pydantic Structured Outputs;
- resumable success JSONL and separate error JSONL; and
- disabled automatic retries.

The prompt did not identify prior representation findings or candidate
families. The evaluated DataSnapshotMetadata schema remained separate from the
SchemaValidationResult and CandidateGap output models.

### 2.3 Calibration

Calibration was methodological and excluded from substantive counts.

| Run | Calls | Result | Interpretation |
|---|---:|---|---|
| Calibration0: complete v1.2 | 12 | 11 no-gap; one possible component-structure gap | Confirmed input resolution, nested paths, output consistency, and the field-coverage threshold |
| Calibration1: provenance ablation | 1 | One critical data-source gap and one possible methodology-note gap | Passed the pre-specified provenance sensitivity signal |

Calibration0's single candidate concerned the association of titles,
visualization forms, variables, temporal scopes, and comparators with
components of a composite snapshot. It closely reproduced the panel issue
already observed in Validation 2.

Calibration1 locally removed provenance and interpretive_notes from the
generated schema supplied for document_699863_table_004.png. The model
identified the displayed CIDTc data source as a critical gap. This establishes
sensitivity to that particular omission, not general candidate recall.

No additional calibration rounds were introduced. This avoided adapting the
instrument to the substantive candidate patterns it was intended to measure.

### 2.4 Execution and traceability

The
[execution notebook](1.0-schema_validation3.ipynb)
retained the Validation 2 execution style. Successful records stored input
identity, schema version, request configuration, parsed output, raw response,
token usage, and elapsed time.

The
[analysis notebook](2.0-schema_validation3_analysis.ipynb)
checked filename coverage, duplicate filenames, API status, unresolved errors,
schema version, excluded-field state, configuration consistency, and agreement
between snapshot assessments and candidate statuses. It also prepared the
candidate tables and image inspector used during adjudication.

### 2.5 Human adjudication

All 36 candidates received a final disposition. Distinct and potentially
consequential cases were inspected individually. Highly repetitive map-scale,
coordinate-extent, and hierarchy candidates were adjudicated by applying an
agreed family-level rationale after inspection of representative examples.
This reduced repetitive image review without treating candidate frequency as
evidence of acceptance.

For each candidate, review considered:

- whether the information was explicitly evidenced;
- whether it described the data snapshot rather than its parent document;
- whether it was reusable metadata rather than extracted content;
- whether existing v1.2 paths represented it adequately at snapshot level;
- whether omission materially affected interpretation or discovery; and
- whether the issue was conceptual, representational, or documentary.

No no-gap result was independently audited. The analysis therefore does not
estimate false-negative frequency or model recall.

## 5. Human adjudication

### 5.1 Outcome counts

| Human decision | Candidates |
|---|---:|
| Covered adequately by v1.2 | 7 |
| Extraction or internal visual structure | 13 |
| Insufficient evidence, generalizability, or materiality | 11 |
| Outside the snapshot-metadata boundary | 1 |
| Documentation or representation concern, not accepted as a new field | 3 |
| Accepted meaningful representation gap | 1 |
| **Total** | **36** |

No candidate was accepted as a new standalone metadata field.

### 5.2 Cartographic representation

Eight candidates proposed a dedicated map-scale or scale-bar field. Human
review found that cartographic scale would be useful in a catalog of printed
maps but had insufficient independent value for the general data-snapshot
schema. Metadata is not expected to substitute for viewing the map when
measuring distances.

Four candidates proposed numeric coordinate or bounding extents. These values
would require extraction of the map's graticule or footprint. Existing
geographic_coverage fields adequately describe the snapshot's named
geographic scope for the intended metadata use.

All 12 cartographic candidates were rejected.

### 5.3 Hierarchy and internal structure

Four candidates requested recursive category hierarchies deeper than the
single category-group level supported by dimensions[].category_groups. The
implemented category-group structure was the v1.2 response to the hierarchy
finding from Validation 2. Extending it recursively would move the metadata
schema toward reproducing table rows, subtotals, components, and cells.

The remaining three candidates requested categorical visual-encoding roles, a
conditional percentage denominator, and a directed financial decomposition.
These describe internal chart or diagram structure and belong to extraction.

All seven hierarchy and internal-structure candidates were classified as
extraction content rather than missing metadata fields.

### 5.4 Scoped associations

The model proposed variable-specific time, geography, provenance, targeted
notes, multiple periods, and panel-specific metadata.

Human review retained the snapshot as the unit of analysis:

- temporal_coverage describes the overall represented-data period;
- geographic_coverage describes the overall geographic scope;
- complete source-visible variable labels and subject_summary can preserve
  relevant qualifiers;
- interpretive_notes can preserve explicit note text without reproducing
  note-to-cell bindings; and
- variable-specific temporal or geographic scopes were not added.

Variable-level provenance identified a potentially useful refinement of the
existing provenance representation. One instance did not justify introducing
a new nested source-association structure. The observation is retained as a
future documentation or representation concern.

The two panel_metadata candidates reproduced a known Validation 2 issue. The
current v1.2 working design retains ordered panel_titles and snapshot-level
visualization_types. The Aivin review already asks whether a minimal panels
collection containing only title and visualization_type should replace that
flat association. Richer per-panel periods, subjects, variables, and measures
remain outside the intended boundary.

Of the seven scoped-association candidates, four were considered adequately
covered and three were retained as representation or documentation concerns.
None was accepted as a new field.

### 5.5 Value and observation semantics

Two value_status candidates concerned baseline, current, target, or projected
values. Existing temporal, dimension, comparison, and note fields can preserve
those source-visible distinctions without a dedicated value-status field.

The respondent_group candidate was adequately covered through title and
subject_summary. The unit_of_analysis candidate distinguished the measured
variable from the entity underlying a distribution, but the reviewed
histogram did not state that entity clearly enough to establish a reusable
field. A source-supported subject_summary can preserve it when relevant.

Data-collection responsibility occurred as operational content in a
specialized project-results table. It belongs to project or document workflow
context rather than the reusable metadata of the data snapshot.

No candidate in this family warranted a new field.

### 5.6 Visual-axis encoding

Axis truncation and nonzero axis-range proposals would require extracting
visual scale behavior. They remain chart-encoding content rather than general
snapshot metadata.

The axis_scale_assignment candidate was different. The snapshot explicitly
assigned different measured variables to distinct y-axes. The evaluated
variables[].analytical_roles could identify a general y-axis role but could not
bind each variable to the appropriate scale. Applying the wrong axis would
materially change the interpretation of the values.

Human review therefore accepted this as a meaningful representation gap within
the existing variable concept. It did not warrant a top-level field. The
post-validation v1.2 model now provides variables[].axis_assignments with:

- dimension: x or y;
- position: top, bottom, left, or right; and
- position_index: one-based order from the plotting area outward for multiple
  axes on the same side.

This representation supports ordinary left/right dual-y graphs, multiple
x-axes, and multiple axes on the same side without extracting axis ranges or
tick values. General single or shared x/y roles remain available through
variables[].analytical_roles.

### 5.7 Rare relationships and labels

The cross-snapshot reference candidate identified a real relationship between
a table and an explanatory note in another table. It was not raised for the
same snapshot in Validation 2 and appeared only once in Validation 3. It is
recorded as a potentially useful future relationship, but current evidence and
materiality do not justify a dedicated field.

The icon-only column-label candidate was also a single rare case. Representing
it structurally would require inventing meanings not supplied by an explicit
legend. It did not warrant a field.

## 7. Relationship to Validation 2

Validation 2 returned 197 no-gap assessments, five possible-gap assessments,
and no critical assessments. Validation 3 returned more positive model
assessments, but candidate count is not the study conclusion.

The paired snapshot-level assessments were:

| Validation 2 assessment | V3 no gap | V3 possible | V3 critical | Total |
|---|---:|---:|---:|---:|
| No critical gap found | 168 | 27 | 2 | 197 |
| Possible gap | 3 | 1 | 1 | 5 |
| Critical gap found | 0 | 0 | 0 | 0 |
| **Total** | **171** | **28** | **3** | **202** |

The instrument intentionally changed both schema content and schema
representation: v1.1.1 Markdown was replaced by generated v1.2 JSON Schema.
Individual model calls are also nondeterministic. The observed assessment
differences therefore cannot be attributed to Pydantic, JSON Schema, a
particular v1.2 change, or model variability separately.

Human adjudication provides the relevant comparison. Validation 2 accepted no
new field and deferred two representation issues. Validation 3 likewise
accepted no new metadata concept. It found one new actionable representation
limitation within variables. The panel concern repeated; the deeper hierarchy
proposals did not overturn the implemented nonrecursive category-group
boundary.

The larger model-generated review set therefore does not imply that v1.2
misses more accepted fields than v1.1.1.

## 8. Main findings

### 8.1 The v1.2 field inventory is stable

None of the 36 model-generated names survived human review as a new standalone
metadata field. Existing concepts covered seven candidates, while 25 were
extraction-oriented, outside scope, or insufficiently evidenced or material.
Three more were retained as documentation or representation concerns rather
than fields.

The accepted conclusion concerns the field inventory after adjudication, not
the number of candidates generated:

> The tested corpus does not support extending the accepted v1.2 metadata
> concept inventory.

### 8.2 The accepted new finding is structural

The dual-axis candidate exposed a real association that the evaluated schema
could not represent: which distinct axis applies to each variable. The
relevant concepts—variables, analytical roles, units, and axes—already existed.
The deficiency was their relationship.

The appropriate response was therefore a nested addition to Variable rather
than a new top-level axis field. This is a structural improvement to an
existing concept, not expansion of the field inventory.

### 8.3 Snapshot-level scope prevents extraction creep

Repeated candidates requested map calibration, coordinate bounds, recursive
table hierarchies, conditional denominators, note-to-cell targets, and diagram
flows. These could make a machine reconstruction of the snapshot more
complete, but that is not the purpose of the metadata schema.

Keeping the data snapshot as the unit of analysis allows the schema to retain
subjects, variables, dimensions, periods, geography, provenance, and
interpretive context without becoming a general chart, table, map, or diagram
extraction format.

### 8.4 Existing representation questions remain bounded

Panel title-to-visualization-type association remains an open design question
for Aivin. The current preference is a minimal descriptor if any per-panel
structure is adopted. Rich panel-specific metadata was not supported.

Variable-level provenance and cross-snapshot reference candidates are worth
retaining as future observations. Neither was sufficiently recurrent or
material in this exercise to justify changing the schema.

## 9. Post-validation schema amendment

The substantive run evaluated v1.2 before variables[].axis_assignments existed.
Human adjudication then produced the following canonical-model amendment:

- AxisAssignment records dimension, position, and position_index.
- Variable contains an optional axis_assignments collection.
- x-axis assignments accept top or bottom positions.
- y-axis assignments accept left or right positions.
- position_index distinguishes multiple axes on the same side.
- analytical_roles continues to represent general single or shared x/y roles.

The canonical Pydantic model, generated JSON Schema, generated field reference,
concept design, README, public exports, and tests were updated together.
Generated-artifact checks and the full test suite passed.

This amendment is an outcome of Validation 3. It must not be described as part
of the schema supplied to the completed API calls.

## 10. Limitations and claim boundary

- Validation 3 evaluated 202 snapshots from three institutional corpora. The
  result may not generalize to every document domain or visualization
  practice.
- It reused the Validation 1 and Validation 2 corpus and is not an independent
  sample.
- The assessment used one resolved model snapshot and one final prompt
  configuration. Another model run may surface a different review set.
- No-gap cases were not independently audited. The exercise does not estimate
  recall or a false-negative rate.
- Repetitive candidates were adjudicated using family-level rationales after
  representative inspection rather than separate extended image review for
  every occurrence.
- The provenance control demonstrated sensitivity to one pre-specified
  omission only.
- Candidate rarity supported some decisions but was never the sole rejection
  criterion.
- The design changed schema content and representation together. It cannot
  establish that Markdown-to-Pydantic implementation caused any difference.
- The canonical v1.2 schema was amended after the run. Conclusions about the
  evaluated schema and the post-validation version must remain distinct.
- Stability means that no new consequential metadata concept was accepted from
  the tested evidence. It does not guarantee universal completeness.

## 11. Conclusion

Validation 3 processed all 202 substantive snapshots without technical
failure. It produced 36 candidate records across 31 snapshots, including three
model-rated critical candidates.

Complete candidate disposition accepted no new standalone metadata field.
Most proposals were adequately covered, outside the snapshot boundary,
extraction-oriented, or insufficiently general and material. Panel metadata
reproduced a known question rather than revealing a new omission.

One candidate survived as a meaningful representation gap: the evaluated
schema could not bind variables to distinct axes in a multi-axis graph. The
post-validation v1.2 amendment now represents that relationship through
variables[].axis_assignments.

The result therefore changes the Validation 2 formulation only slightly. The
field inventory remains stable, and the representation improvements introduced
in v1.2 address the tested concepts without exposing a new missing metadata
subject. Validation 3 added one bounded structural refinement to Variable,
while leaving the snapshot-level schema boundary intact.
