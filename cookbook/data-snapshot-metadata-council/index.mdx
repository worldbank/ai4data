# Practical Guide to Refining Data Snapshot Metadata Extraction Policies with Model Councils

**A cookbook for data scientists, ML engineers, and AI application developers.** Version 0.1 (working draft), November 2026.

:::note[Working draft]
This guide documents a proposed experiment. The snapshots and published human-reviewed annotations are real. All round extractions, reviews, deliberations, and policy revisions are illustrative. The council experiment has not been executed.
:::

Metadata extracted from a data snapshot can conform to the schema even when the model assigns an axis label to the title field or infers a value that the snapshot does not support. These errors can help identify where the *extraction policy*, the instructions that guide the model, needs to be more precise.

This guide proposes an experiment that uses a council of models to refine an initial extraction policy. The council uses findings from each review round to propose and critique changes. The experiment aims to develop a metadata extraction pipeline by pairing a fixed reference extractor with the final policy. The guide starts with a prepared example so the team can see how an error becomes a candidate rule before setting up a round.

## Prerequisites

The walkthrough uses the examples supplied with the guide. For a round using the team's own data, the following are needed.

- Familiarity with multimodal model inference, prompts, structured outputs, and basic evaluation.
- Existing data snapshots, their source references, and the [Data Snapshot Metadata Schema v1.4 reference](/docs/data-snapshots/metadata-schema/).
- A human reviewer who understands the metadata schema and can assess extraction issues against the source evidence.

## First steps

1. Start with the prepared D1 example in [the workflow chapter](./workflow.mdx). Follow one title error from the data snapshot to a proposed policy revision. Allow about an hour.
2. Use [the preparation chapter](./preparation.mdx) to set up a round. Verify the data snapshots and their references, then record the starting policy and settings. Allow about two hours.
3. Use [diagnosis](./diagnosis.mdx) to establish what went wrong and [deliberation](./deliberation.mdx) to decide what to change. Allow about two hours for discussion.

Once the review workflow is clear, [chapter 5](./orchestration.mdx) shows where agent orchestration and tools fit. [Chapter 6](./progress.mdx) explains when to stop revising and how to evaluate the result. The [self-assessment](./start-here.mdx) helps teams decide where to start.

## Running example

The [Data Snapshot dataset](https://huggingface.co/datasets/ai4data/data-snapshot) contains more than 3,900 data snapshots. The [gold metadata release](https://huggingface.co/datasets/ai4data/data_snapshot_metadata_gold) contains 102 human-reviewed records. The walkthrough uses the following four data snapshots, two with human-reviewed annotations.

| Sample | Batch | Snapshot and focus |
|---|---|---|
| D1 | Discovery | The Shona labor-force chart distinguishes a caption from an axis label. |
| D2 | Discovery | The WPS5070 rural Indonesia regression table distinguishes variables, statistics, and lag groupings. |
| C1 | Challenge | The Shona demographics table shows row-specific units but omits the caption. |
| C2 | Challenge | The WPS4771 guarantee-systems chart shows categories and legend entries but does not identify the counted entity. |

The sample register pins the dataset revisions, source pages, and image fingerprints. The [preparation chapter](./preparation.mdx) explains the pairings and reuse information.

## Scope of the examples

The example illustrates one round, from the starting policy and state (P001 and S001) to the candidate policy and updated state (P002 and S002). The walkthrough uses selected fields to make each decision inspectable. Observations across rounds would be needed to assess stabilization, and independent evaluation would measure extraction quality. Distinguishability judging, fine-tuning, and operational deployment are outside this design.
