# 5. Pi orchestration and deterministic controls

**Question:** How could the proposed workflow be coordinated reliably?

## Rationale

Pi is the proposed harness, the software that would start model sessions, coordinate stages, and record handoffs. The orchestrator model from [chapter 4](./deliberation.mdx) would write the next policy and state. The harness would check and save those outputs before starting the next stage.

Give scripts or tools the steps with exact rules, such as checking sample IDs or assigning version numbers. For each round, the harness would pass the selected policy and data snapshots to the fixed reference extractor. It would validate the resulting metadata against the schema and save the records with the policy version used for extraction.

## Target state

- A proposed Pi workflow names its model roles, permitted inputs, deterministic operations, and human checkpoints.
- Each stage has a completion condition and a way to resume from validated artifacts.

## Maturity levels

| Level | Steps |
|---|---|
| **Foundational** | Document the sequence and review inputs and outputs at each handoff. |
| **AI-ready** | Specify deterministic checks and record stage completion in the manifest. |

## Recipes

<Recipe title="5.1 Map the round to Pi sessions and tools" level="AI-native" skills="Application developer and experiment lead" time="60 minutes">

**Result:** An integration specification separates model work from deterministic tool behavior.

Consider what two Pi sessions would receive for D2. The judge needs the image, extraction, and full human-reviewed annotation. A council member needs the image, extraction, relevant findings, and the summary of human decision H01. Those two sets of inputs are examples of role packets.

Plan a separate session for each model role. Specify how tools assemble and check each packet before passing it to the session.

| Proposed operation | Input | Output and completion check |
|---|---|---|
| Select and register samples | Pinned inventory, split rules, selection settings | Ordered sample IDs and verified image and reference associations. |
| Resolve settings and create the round | Model and rubric configuration, policy, state, schema | A manifest with versions and fingerprints. Reject missing or inconsistent settings. |
| Assemble role packets | Role and validated artifact references | A packet with the evidence files and fields authorized for that role. Verify that council sessions have no access to full gold annotations. |
| Validate stage records | Generated records, expected IDs, schema or stage contract | Valid records and explicit failures. Confirm coverage and uniqueness. |
| Write the next versions and ledger | Synthesis, prior policy, human dispositions | Versioned policy, state, findings, and rule counts with resolvable references. |

1. Give the reference extractor and judge fixed configurations. Specify how the harness passes the current policy to the extractor and checks its output against the schema. The policy used in the example is [P001](pathname:///cookbook-files/data-snapshot-metadata-council/001_policy.md).
2. Specify that the judge receives full Discovery references. Limit council sessions to the evidence and findings prepared for them. Restrict file, shell, and network access so council tools cannot retrieve the full annotations.
3. Separate the three initial council contexts. Enable the critique stage only once all initial proposals are recorded. Route the revisions to the distinct synthesis model.

**Worked example.** The selection tool would verify D2’s image against the checksum in the sample register. The packet assembly tool would use that register to locate the full annotation for the judge and share only the authorized files and fields with the council.

**What this does not do.** This recipe specifies the proposed harness. Its tools and handoffs still need to be implemented and tested.

</Recipe>

<Recipe title="5.2 Define checkpoints and recovery" level="AI-ready" skills="Application developer and human reviewer" time="45 minutes">

**Result:** The workflow has a transition table and an explicit recovery procedure.

Suppose the judge saves valid reviews for D1, D2, and C1, and then the round is interrupted before it saves C2’s review. The three saved records are available for reuse, but the batch is still waiting for one review. Use checkpoints to record what is ready and what must happen before deliberation can start.

| Transition | Gate |
|---|---|
| Prepare to extract | Confirm sample identity, settings, and starting versions. |
| Extract to diagnose | Validate one output per expected sample or record a blocked stage and the failures. |
| Diagnose to deliberate | Confirm review coverage and record human dispositions or explicitly open issues. |
| Propose to critique to revise | Check that the expected members contributed at each phase. |
| Synthesize to handoff | Validate the new versions, tally rule changes, and persist the findings before advancing. |

1. Record stage status and the artifact path or failure reason. Store an attempt separately if a model call needs retrying.
2. Resume the first incomplete stage with the original input versions. Reuse validated results from those inputs. If an interrupted request left no valid result, record the retry as a new attempt.
3. Pause for escalations that require a human decision before deliberation, such as F03. Record the disposition and obtain authorization before using a changed reference or schema.
4. Make the transition to the next version explicit. Preserve the prior policy and records so an interrupted write cannot replace them.

**Worked example.** On resuming, the runner would keep the three saved reviews and request C2’s review using [P001](pathname:///cookbook-files/data-snapshot-metadata-council/001_policy.md) and the same rubric. The round could move to deliberation once the review is valid and saved and any required human decisions are recorded.

**What this does not do.** The transition table does not demonstrate that retries, model calls, or Pi sessions work in this repository. Those behaviors require implementation and testing.

</Recipe>

## Implementation options

- Use separate Pi invocations with limited inputs. If an application needs to start or manage sessions from code, consider Pi's remote procedure call (RPC) interface or software development kit (SDK).
- Keep deterministic checks and version writes in ordinary scripts or constrained tools. Use process isolation or an equivalent control when a role could otherwise read restricted files.

## Resources

- The [Pi CLI integration guide](https://pi.dev/docs/latest/cli-integration) documents interfaces for external controllers.
- The [Pi documentation](https://pi.dev/docs/latest) describes tool permissions and session interfaces.
- The [schema reference](/docs/data-snapshots/metadata-schema/) describes the structure and validation rules for extraction output.

## Common mistakes

- Letting a model pick samples or rewrite a manifest can change the experiment conditions without a recorded decision.
- Sharing a working directory with unrestricted tools can expose the gold annotations despite prompt-level restrictions.
- Advancing after an incomplete stage can turn missing evidence into apparent agreement.

## Verification

- Walk the proposed transitions using the illustrative files and check the required inputs at each gate.
- Inspect the proposed permissions as well as prompt contents. Confirm the council cannot obtain the gold through tools or shared histories.
- Describe one incomplete-stage scenario and identify what can be retained and what must be recovered.
