# 3. Diagnostic assessment and human review

**Question:** How are extraction problems assessed and escalated?

## Rationale

Schema validation checks the structure of a metadata record. The judge then checks whether the field represents what the image shows and follows the policy used to produce it. For example, both a caption and an axis label are text, so schema validation alone cannot tell which belongs in the title field.

The diagnostic judge makes the first assessment. The human reviewer resolves findings that require a decision and spot-checks other cases.

## Target state

- Each review names the sample, examined fields, evidence, uncertainty, and escalation status.
- Human decisions record the disposition and any authorized change to gold or schema.

## Maturity levels

| Level | Steps |
|---|---|
| **Foundational** | Compare extracted fields with the image and document the reasons for escalation. |
| **AI-ready** | Use a fixed diagnostic rubric and structured finding and decision records. |
| **AI-native** | Specify a gated review stage with separate inputs for Discovery, Challenge, and council roles. |

## Recipes

<Recipe title="3.1 Specify a diagnostic review" level="AI-ready" skills="Metadata reviewer and ML engineer" time="45 minutes">

**Result:** A set of review questions and a record format capture the evidence, assessment, and need for human review.

Use the following assessment questions as a fixed rubric for both batches. On Discovery, a difference from the human reference prompts a check against the image and can reveal a reference issue. On Challenge, the judge applies the same checks using the image, schema, and policy.

| Check | Question |
|---|---|
| Evidence support | Does the visible image support the value and the role assigned to it? |
| Metadata completeness | Which relevant values supported by the data snapshot are missing? Distinguish schema requirements, relevant optional fields, and details the image cannot establish. |
| Policy compliance | Does the output follow the rules in the executed policy? Cite the applicable rule IDs. |
| Uncertainty | Which interpretations remain plausible, or what evidence would resolve the question? |
| Human escalation | Does a consequential ambiguity, unresolved reference dispute, or proposed schema change require human adjudication before proceeding? |

1. Provide the image, generated metadata, schema, and policy used for extraction. In round 001, that policy is [P001](pathname:///cookbook-files/data-snapshot-metadata-council/001_policy.md). Include the full human annotation for Discovery. Mark reference comparison unavailable for Challenge.
2. Record the fields examined in `review_scope`. For each finding, identify its kind, field, visual evidence location, applicable rule IDs, and assessment. Use `uncertainty` for a short description of what the evidence leaves open, or null when nothing material remains uncertain for that finding.
3. Set `human_attention` to true when a person needs to resolve the finding before the round can proceed. Use `attention_reason` to explain the decision for either value.
4. Share the finding with the council once any required human decision is recorded. Include the image evidence needed to inspect the issue and keep the full annotation in the judge and human review materials.

**Worked example.** The table pairs selected fields from the illustrative P001 outputs with evidence from the four data snapshots in [chapter 2](./preparation.mdx). Each finding covers the field or fields shown.

| Sample | Selected illustrative output | Visual evidence and diagnostic finding |
|---|---|---|
| D1 | `title = "Percent of population"` | **F01.** The phrase runs along the vertical axis. A separate caption above the chart identifies the labor-force figure. The words appear in the image, but their placement contradicts the assigned title role. |
| D2 | `Log PCE` is an `outcome`. `Monsoon Onset` is a `predictor`. `SE` appears as its own variable. | **F02.** The table identifies Log PCE as the dependent variable and lists Monsoon Onset as a regression term. Under both lag specifications, `Coef` and `SE` label the coefficient and standard error reported for each term. The output treats `SE` as a variable in its own right. |
| C2 | `name = "Number of countries"`, `unit.source_text = "countries"` | **F04.** The scale has ticks but no unit label. The category labels and legend identify groupings without establishing what is counted. The entity remains uncertain, but the image gives enough evidence to flag the unsupported wording under R01 and R04. |

F01 and F02 can go to the council because the layout resolves the field-role questions. F04 can also go to the council because the unsupported value can remain unset under P001. None requires a reference or schema decision. [Illustrative extraction records](pathname:///cookbook-files/data-snapshot-metadata-council/001_extractions.jsonl) · [Illustrative judge reviews](pathname:///cookbook-files/data-snapshot-metadata-council/001_judge_reviews.jsonl)

**What this does not do.** Judge findings are provisional assessments. The abbreviated review scopes in the example do not demonstrate full-record coverage or judge accuracy.

</Recipe>

<Recipe title="3.2 Record the human decision and its scope" level="Foundational" skills="Metadata reviewer" time="30 minutes">

**Result:** A review record documents decisions and identifies what information can carry forward.

Use the same rubric for escalated and spot-checked cases. The value `human_attention: false` means the finding can proceed without immediate human adjudication. An extraction error can still be present, as F01 shows. Human spot checks can reveal missed errors or narrow review coverage.

1. Review escalated findings and select additional cases for a spot check. Inspect the image, output, policy used for extraction ([P001](pathname:///cookbook-files/data-snapshot-metadata-council/001_policy.md) in round 001), and reference where available. Record which fields were checked.
2. Record a decision and its reason. For an approved gold or schema correction, record the old and new versions and preserve the original evidence.
3. Pass the decision and its reason to the council and orchestrator. In [chapter 4](./deliberation.mdx), these summaries accompany the findings used to propose rule changes.

**Worked example.** F03 escalates D2's interpretation note because assigning significance thresholds to the stars would affect how a reader interprets the estimates. Both the illustrative extraction and gold preserve “See notes to table 1.” The data snapshot omits the referenced notes. In H01, the reviewer keeps the cross-reference and leaves the thresholds unspecified. The gold and schema versions stay the same.

C1 has an empty findings list for the reviewed fields. H02 still checks its median-age unit and year categories and confirms that the title can remain null for C1. That spot check covers the named fields only. [Illustrative human review](pathname:///cookbook-files/data-snapshot-metadata-council/001_human_review.md)

**What this does not do.** These authored decisions demonstrate the record structure. They supply neither verified model behavior nor a measured judge agreement rate.

</Recipe>

## Implementation options

- Use a table to try the rubric on a small set of images. Move to a JSON Lines contract when reviews are handed off automatically.
- Calibrate the diagnostic judge separately against reviewed cases before relying on its coverage. Record rubric changes as changes to the experiment conditions.

## Common mistakes

- Counting a structurally valid record as correct bypasses the image evidence.
- Interpreting an unflagged record as fully reviewed overstates the judge's coverage.
- Letting a diagnosis revise policy or gold collapses distinct responsibilities.

## Verification

- Check that Discovery and Challenge reviews declare the correct reference status.
- Trace each escalation to a human disposition or an explicitly open case.
- Verify that council-facing findings cite image evidence and omit complete annotations.
