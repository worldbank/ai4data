# 5. Combined execution and output structure

**Question:** How are both stages invoked together?

## Rationale

The previous chapters showed snapshot extraction, metadata extraction, and output inspection step by step. This chapter brings the two extraction stages together in one command: it extracts data snapshots from the PDF, then generates metadata for the resulting images.

The example uses one PDF to show the command and expected output structure. The same command can process a directory of PDFs, searching its subdirectories recursively. This extends the workflow to a collection of documents without running separate commands for each stage or PDF.

## Target state

- The reader can use the end-to-end runner for a PDF or directory of PDFs.
- The reader can locate the resulting images and metadata files and account for paid metadata requests.

## Maturity levels

| Level | Steps |
|---|---|
| **Foundational** | The organization completes snapshot and metadata extraction as separate steps and can match each selected image to its description. |
| **AI-ready** | A developer can configure the combined entry point, identify its output pairs, and account for metadata requests across all newly extracted candidates. |
| **AI-native** | An organization integrates both stages with monitored request volume, output checks, and human review. The combined command alone does not provide that wider operational system. |

:::info[Running example]
The sample PDF used in the tutorial illustrates the combined command and expected PNG and JSON output structure. The tree shows all eight image files and their matching metadata filenames.
:::

## Recipes

<Recipe title="5.1 Run both extraction stages with one command" level="AI-ready" skills="Developer and data curator" time="Ten minutes to prepare the command; execution time varies">

**Result:** One command performs snapshot extraction and then metadata extraction for the supplied input.

The command below processes the sample PDF through both stages. Use a fresh output directory because PDFs with existing matching outputs are skipped. Confirm that the selected provider's API key is set as described in [Recipe 1.2](./preparation.mdx#recipe-1-2).

:::warning[Token costs]
Metadata requests incur token costs for every newly extracted image, including irrelevant detections. A directory containing multiple PDFs can generate many requests.
:::

```bash
python -m ai4data.data_snapshot \
  --input=data/policy_brief_on_shona_community_from_stateless_to_citizens.pdf \
  --output-dir=output/cookbook-data-snapshot-combined \
  --device=cpu \
  --metadata-provider=openrouter
```

If a compatible NVIDIA GPU and CUDA runtime are available, select GPU inference with `--device=cuda:0`. The recorded example uses CPU. An unavailable CUDA device causes an error; there is no automatic CPU fallback.

To process a collection, set the `--input` parameter to a directory containing PDFs. Subdirectories are searched recursively. Each PDF must have a unique filename stem, including across subdirectories, because outputs share the same detector folders.

1. Confirm that the input PDFs are ready and set `--input` to the PDF or directory
2. Choose a fresh output destination and set the `--output` parameter to it.
3. Run the command, then inspect the generated images and JSON files.

**Worked example.** A successful combined run of the sample PDF produces eight PNGs and eight JSON files.

**What this does not do.** The combined command does not roll back an entire run after failure. Extraction errors can prevent metadata processing; metadata errors stop at the failing image while earlier files remain.

</Recipe>

1. Match files by their complete stems because source names can contain underscores.
2. Inspect missing JSON as a possible incomplete metadata stage. The PNG may still be valid.
3. Page coordinates and provider usage logs are not written in this tree.

**Worked example.** Each successfully processed data snapshot has a PNG in `snapshots/` and a matching JSON in `metadata/`. With directory input, files from all input PDFs share these folders, with each source PDF's filename stem identifying its outputs.

**What this does not do.** Matching filenames do not establish metadata accuracy. The image and JSON still need inspection together.

</Recipe>

## Implementation options

Directory input extends the workflow to multiple PDFs; processing remains sequential. Use a new output directory when changing the input collection or configuration to preserve earlier results.

Use the separate commands when a curator needs to select data snapshots before incurring metadata costs.

Python callers can use `run_pipeline(input_path, output_dir, model_name="doclayoutyolo", device="cpu", metadata_provider="openrouter")`. It returns new snapshot paths followed by metadata paths. A fully skipped PDF command returns no new paths.

## Common mistakes

- Running combined execution after snapshot-only in the same root skips the PDF and leaves missing JSON unfilled.
- Assuming that every image has metadata can hide a partial failure.

## Verification

- Use `output/cookbook-data-snapshot-combined` as a fresh destination, separate from `output/cookbook-data-snapshot`, so the prior data snapshots do not trigger PDF-level skipping.
- Read the expected tree by matching complete PNG and JSON stems. For directory input, check the outputs belonging to each PDF's filename stem.
- Check that each generated PNG has a matching JSON. Investigate missing metadata files or reported errors before treating the run as complete.
