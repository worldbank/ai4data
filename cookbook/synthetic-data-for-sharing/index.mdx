# Practical Guide to Synthetic Data for Sharing

**A cookbook for microdata teams and methodologists in national statistical organizations.** Version 0.1 (working draft), October 2026.

:::note[Working draft]
This guide is a working draft from the AI for Data – Data for AI program. It
collects practical approaches and open standards. It does not
represent official World Bank Group guidance or policy and is not legal
advice; an organization applies it under its own statistical law, data
protection rules, and institutional policies.
Comments and corrections are welcome as
[GitHub issues](https://github.com/worldbank/ai4data/issues), and the
[contributing](./contributing.md) page explains how to propose a recipe.
:::

Microdata are the most requested and the least shareable product a
statistical organization holds. Every applicant for a licensed file waits,
then discovers on the real file what the documentation did not say.
Students, developers, and partners who cannot receive the real file
receive nothing. A synthetic file, generated by a model fitted to the real
microdata so that it has the same shape and similar relationships while
containing no real record, answers these needs: code is written and
tested before the application, teaching has a realistic file, pipelines
have test data, and partners have something to work with. It does not
answer the need for estimates, and this guide keeps that line.

This guide is organized around seven questions. The first settles what
synthetic data are for and what they are not for. The next two are
about making a file: which synthesis method fits the data, and how
multi-table and longitudinal data are synthesized. Two are about
measuring it: how utility is measured, and how disclosure risk is
measured. The last two are about releasing it: how a release is
documented and governed, and how synthetic data enter the access and
analysis workflow. Each chapter answers one question with recipes,
maturity levels, worked examples, and a checklist.

The recipes build on the program's synthetic data workstream, whose
[REaLTabFormer](https://github.com/worldbank/REaLTabFormer) generates
tabular and relational synthetic data with a built-in control on
memorization, on the sequential synthesis methods established in official
statistics (synthpop), and on the disclosure control practice of the
[sdcMicro practice guide](https://sdcpractice.readthedocs.io/). The
[standards page](./standards.md) lists each and where it applies.

:::tip[Three rules for synthetic files]
Three rules run through the guide: every synthetic file has a utility
report and a risk review before release; every file is labelled synthetic
in its name, its record, and its data; and no statistic is published from
one. A synthetic file that meets the three is a service; one that misses
any of them is a risk.
:::

## Prerequisites

The recipes assume the following are in place or can be arranged:

- A microdata file users request often, its documentation, and the unit that owns it.
- A methodologist with R or Python, and the disclosure control unit that sets the limits.
- For the AI-ready level, a server inside the organization to run the synthesis and the reports; for generators, a GPU.

## First steps

For a team with limited time, this sequence gives the most useful result first:

1. Write the purpose statement of [chapter 1](./purpose.mdx) and choose the one survey to start with. This takes half a day.
2. Synthesize it with a sequential method, with the seed recorded, following [chapter 2](./method.mdx). This takes a day.
3. Run the utility report and the risk report of [chapters 3](./utility.mdx) and [4](./risk.mdx), and fix the method until both pass the limits. This takes one to three days.
4. Write and check the synthesis record, label the file, and release it beside the real survey with a guidance note, following [chapters 6](./release.mdx) and [7](./workflow.mdx). This takes a day.

Relational and panel data ([chapter 5](./relational.mdx)) come after the first single-table file has users.

## Self-assessment

The [self-assessment](./start-here.mdx) takes about five minutes and places
a microdata team's synthetic data practice at a level in each chapter.

## Maturity levels

Each chapter describes three levels. A team can sit at different levels in
different chapters, and the first level is a complete, useful state on its
own.

| Level | Meaning |
|---|---|
| **Foundational** | One synthetic file produced with a sequential method, measured, labelled, documented, and offered beside the real survey. |
| **AI-ready** | Synthetic files for the main surveys with methods chosen by rule, utility and risk measured against thresholds and limits, records checked, and the files placed in the access workflow. |
| **AI-native** | Synthesis as a pipeline stage at each release, relational and panel structure preserved and checked, reports published with the files, and use tracked. |

## Running example

The labour force survey of the example organization, in a 300-record
extract with six variables, synthesized by the crudest possible method
so that the utility and risk reports have something to find: a lost
association, a wrong employment rate for men, and fifteen copied records.
A pair of forty households and 128 persons with planted structural faults
carries the relational check, and a synthesis record for the real
release carries the documentation check. All records are invented.

## Scope of the examples

The examples are small on purpose: three hundred records, forty
households, one record, so that a reader can run them in an afternoon and
see the shape of each measure and what a bad synthesis looks like. They
are starting points. Each recipe ends with a **What this does not do**
note that says where the example stops and what the full version adds.
The synthesis itself uses the methods and tools named in chapter 2; the
scripts here measure, check, and document what they produce.
