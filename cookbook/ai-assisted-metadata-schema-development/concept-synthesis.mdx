# 3. Field Profiles and Metadata Concept Synthesis

**Question:** How do local observations become manageable evidence for shared concepts?

## Rationale

Thousands of local observations are difficult to compare directly. A metadata
field profile collects observations with the same proposed field name and
preserves accumulated evidence about that name. Exact-name aggregation is a
deterministic operation. It does not decide that differently named fields mean
the same thing or that a frequently proposed field deserves acceptance.

The same grouping rule can be applied to observations from another artifact
class: retain its original property names, artifact identities, values, and
rationales. A field profile summarizes evidence for a name; that name need not
be geographic_scope, title, or any other property found in the study.

Canonical metadata concept synthesis performs a different transformation.
It compares the meanings supported by profiles and proposes shared descriptive
concepts. A concept has a definition and rationale that apply across local
observations. The candidate inventory makes expert review manageable while
preserving unresolved distinctions. It is an intermediate artifact; operational
schema design comes after human refinement.

## Target state

- Exact-name profiles preserve occurrence counts, distinct-snapshot support, and attributable observation evidence.
- Review notes identify plausible semantic relationships and unresolved boundaries using more than the names alone.
- Candidate concept proposals retain their definitions, rationales, and representative fields for human review.

## Learning objectives

- The practitioner can execute exact-name aggregation and explain its denominator.
- The practitioner can distinguish lexical variation from evidence of semantic equivalence.
- The practitioner can propose shared concepts from profile evidence while preserving uncertainty for expert review.

## Prerequisite concepts

[Chapter 2](./discovery.mdx) supplies independent observations and the distinction
between a field name, value, source level, and rationale. The executable exercise
uses Python 3.10 or newer and its standard library. No model, image download,
or API key is required.

| Level | Steps |

## Recipes

<Recipe title="3.1 Aggregate observations into field profiles" level="AI-ready" skills="Python practitioner; metadata reviewer" time="20–30 minutes for the supplied exercise">

**Result:** A new JSON profile records exact-name occurrence count, distinct supporting snapshots, the input denominator, and every contributing observation.

Occurrence count measures how often a name was proposed. Distinct-snapshot
support measures how many different artifacts contributed at least one such
observation. Repeated observations from one artifact increase the first count
without increasing the second. Support is the distinct supporting count divided
by an explicitly identified artifact denominator.

**Input example.** Place [geographic_observations.json](pathname:///cookbook-files/ai-assisted-metadata-schema-development/geographic_observations.json) and [profile_observations.py](pathname:///cookbook-files/ai-assisted-metadata-schema-development/profile_observations.py) in a new working directory. The JSON array contains the three unchanged observations summarized below. Full identities, descriptions, and reasoning remain in that input file.

| Artifact | metadata_field | Recorded observed_value | source_level |
|---|---|---|---|
| Jordan chart | geographic_scope | Jordan, inferred from parent document title and project name; not visible in snapshot | document |
| Afghanistan table | geographic_scope | Afghanistan | snapshot |
| Russian chart | geographic_scope | Russia | both |

1. Open the JSON array and identify snapshot_id and metadata_field in each record.
2. Inspect metadata_field, snapshot_id, observed_value, description, source_level, and reasoning. The three names are identical, but their values and evidence sources differ. Keep the Jordan inference wording intact.
3. Run the command below from that working directory. It groups the exact string in metadata_field without lowercasing, trimming, synonym replacement, or semantic merging. It creates a new output and refuses to replace an existing file.
4. Inspect the profile counts and evidence. Confirm that all three input records remain present and that the denominator counts distinct snapshots across the whole input file.

**Worked example.** The command produces the following summary and writes a
profile in a separate output directory. This is a new deterministic exercise
over recorded observations; it does not rerun metadata discovery.

```bash
python profile_observations.py geographic_observations.json --output outputs/geographic_profiles.json
```

```text
observations: 3; snapshots: 3; exact-name profiles: 1
geographic_scope: count=3, n_snapshots=3, support=1.000
Wrote outputs/geographic_profiles.json
```

**JSON output excerpt.** The following is taken from the generated profile.
The first evidence record is shown unchanged; the other two records are omitted
from this display only. The output file retains all three observations.

```json
[
  {
    "metadata_field": "geographic_scope",
    "count": 3,
    "n_snapshots": 3,
    "total_snapshots": 3,
    "support": 1.0,
    "evidence": [
      {
        "snapshot_id": "027_Jordan-Emergency-Food-Security-Project_figure_001.png",
        "snapshot_type": "figure",
        "source": "refugee",
        "model": "gpt-5.5",
        "metadata_field": "geographic_scope",
        "observed_value": "Jordan, inferred from parent document title and project name; not visible in snapshot",
        "description": "The country, region, or geographic area to which the figure data applies.",
        "source_level": "document",
        "discovery_value": "high",
        "reasoning": "Geographic context is essential for discovery because it is not shown in the figure itself."
      }

  }

```

| Output attribute | Expected value and interpretation |
|---|---|
| metadata_field | geographic_scope is the unchanged grouping key. |
| count | 3 observations use this exact name. |
| n_snapshots | 3 distinct artifact identities support the name. |
| total_snapshots | 3 distinct artifacts occur anywhere in this input file. |
| support | 1.0 is the fraction 3 / 3 for this selected input. |
| evidence | All three original records retain their values, descriptions, source levels, and rationales. |

The script retains all evidence because the exercise is small. The research
profiles instead summarized frequent values, descriptions, rationales, source
levels, corpus coverage, and figure/table occurrence counts. The underlying
observations remained necessary for complete traceability.

For another collection, group the property-name attribute exactly and count
distinct artifact identities separately from occurrences. Choose the denominator
from the intended collection, including an explicit policy for artifacts with
no observations. The exercise calls its identity attribute snapshot_id and
validates the study's source-level labels; an application's records may need
different names or value representations. Preserve the grouping and provenance
rules when adapting those records. Property names follow the new artifact class.

The downloadable script contains the complete deterministic transformation
and safe output handling. It has no external dependencies or model client.

<Recipe title="3.2 Inspect lexical variation and supporting evidence" level="Foundational" skills="Domain reviewer; metadata practitioner" time="30–45 minutes for the title comparison">

**Result:** A documented interpretation identifies a plausible shared concept and preserves distinctions requiring later expert review.

Related names can suggest where to inspect, but they do not establish semantic
equivalence. A caption identifying an entire figure and a heading identifying
one embedded chart can use similar words while serving different roles.
Profile values, descriptions, rationales, and artifact contexts help explain
that distinction.

**Worked example.** Exact-name aggregation preserved three separate profiles.
All counts below are recorded full-study values. The small observation
exercise does not compute these counts.

| Exact name | Observations | Distinct snapshots | Relevant profile evidence |
|---|---:|---:|---|
| figure_title | 84 | 84 | Descriptions include a figure's displayed title or caption. The profile records 81 figure and three table occurrences. |
| table_title | 90 | 90 | Values include project-financing headings and cost-effectiveness summaries; descriptions concern a table title or caption. |
| chart_title | 7 | 7 | Descriptions include embedded-chart or panel titles; values include compound headings and the Russian internal heading. |

1. Select profiles whose names or evidence suggest a possible shared meaning. For the supplied exercise, open canonical-title in [evidence.json](pathname:///cookbook-files/ai-assisted-metadata-schema-development/evidence.json) and use its recorded_profiles input. Its later assignments belong to chapter 4.
2. Compare the exact names and their statistics. Check the object types and source levels as well as the frequencies; a name does not validate the artifact class by itself.
3. Compare descriptions and values in their artifact contexts. Ask whether similar names describe the same object, component, or role. The two Russian headings in independent-naming illustrate this test for whole-object and internal titles.
4. Write a provisional relationship note with the proposed common meaning, evidence for it, and a remaining ambiguity. Retain uncertain distinctions for the synthesis request and human review.

**Teaching interpretation.** The worksheet below is newly written reasoning
based on those records. It is not a recovered historical adjudication log.

| Comparison question | Provisional note |
|---|---|
| Is there a shared descriptive purpose? | The three profiles contain titles or headings useful for identifying analytical content. |
| Is the evidence only lexical? | Definitions, observed values, and retrieval rationales also support a common title-related meaning. |
| What remains unresolved? | A whole-object caption and an internal or panel heading may need a distinction for annotation or representation. |
| What should happen next? | Propose a common concept conservatively and retain the uncertain scope for expert review. |

The Russian caption names fiscal revenues and expenditures broadly. Its
internal chart title identifies total revenue and total expenditure
anti-cyclicality. The difference is visible in the recorded observations
without downloading the image. A shared title-related concept does not require
replacing either original value or silently discarding its role.

**Verification.** A reviewer should be able to explain both the proposed
similarity and the unresolved role distinction using the evidence. A note that
only says the names contain “title” is insufficient. Preserve the original
counts and distinguish them from semantic concept support.

**What this does not do.** The comparison does not accept final concepts,
normalize observation values, or design separate caption and panel fields.
Those conceptual and operational decisions require later human review.

</Recipe>

<Recipe title="3.3 Prepare synthesis and review a candidate concept" level="AI-native" skills="LLM practitioner; metadata reviewer" time="45–60 minutes to prepare and inspect the retained example">

**Result:** A synthesis request specification identifies the profile evidence and expected concept attributes. Review notes explain the recorded title candidate and the distinctions that remain for expert refinement.

The synthesis input is the accumulated profile evidence. Its output describes
shared meanings across the chosen artifact class, according to its intended
uses and diversity. Let the supported meanings determine the candidate inventory's
size; neither 833 input profiles nor 70 output concepts is a target. It is not an exhaustive profile
classification and does not impose a final operational field list. A useful
request makes those limits explicit so that a compact output does not conceal
unresolved conceptual boundaries.

The [synthesis request](pathname:///cookbook-files/ai-assisted-metadata-schema-development/concept_synthesis_request.md) is an independently
written teaching adaptation. It illustrates the instruction and output
structure without running a model or claiming to reproduce the full prompt.

1. Specify the input profiles using their names, descriptions, values, rationales, and occurrence statistics, along with the artifact class and descriptive purpose. Verify that the complete intended input is within the chosen model interface's capacity.
2. Ask for reusable concepts across the contexts represented in the artifact collection, consolidation of clear synonyms, and retention of plausible distinctions when uncertain. Low frequency alone is not an exclusion rule.
3. Specify canonical_name, definition, rationale, and sample_fields for each proposed concept. Treat representative field names as examples; they do not prove that every profile was assigned correctly.
4. Review the recorded candidate below for definitions, unsupported merges, lost distinctions, and ambiguous scope. Preserve the candidate output and input reference before handing it to [expert refinement](./concept-refinement.mdx).

**Worked example.** The recorded synthesis supplied all 833 profiles in one
CSV-supported GPT-5.5 request, with high reasoning and a 12,000-token output
ceiling. The requested approximate range was 50–70 concepts; the retained
Markdown table contains 70 candidates. The following single row is a faithful
excerpt, available under recorded_candidate_concept in canonical-title.

| Candidate attribute | Recorded output |
|---|---|
| canonical_name | title |
| definition | The displayed or inferred title, heading, or caption that identifies the snapshot. |
| rationale | Titles are usually the strongest single searchable description of a snapshot’s content and should be normalized across figures, tables, maps, and charts. |
| sample_fields | table_title, figure_title, snapshot_title, chart_title, map_title, table_caption |

The rationale is the recorded model proposal. It is not a measured comparison
of retrieval methods. The definition's allowance for an inferred title also
remains a candidate boundary for review; it does not authorize inventing a
missing caption. A model-generated concept definition is not automatically
the annotation rule used by the final schema.

The title row illustrates how several exact names can be represented by one
conceptual proposal. The three displayed profiles were only part of the
833-profile input. A new request over those three alone would be a small
demonstration and could not reproduce the complete 70-concept study output.

**Verification.** The prepared request specifies all four output attributes
and identifies the intended profile input. The recorded title candidate contains
those attributes and connects to the displayed profiles. Review notes retain
the unresolved distinction between a whole-object title and an internal heading.
The full study produced 70 candidates; that count is not a target for another
collection or an output of this offline exercise.

**What this does not do.** This recipe does not implement a live synthesis call,
formal ontology relations, profile-to-concept coverage assessment, expert
acceptance, or operational field design. The chapter ends at 70 candidate
concepts. Human refinement and the later 41-concept assessment remain separate.

</Recipe>

## Expected artifact

The general workflow produces exact-name profiles and a provisional concept
inventory for human review. Their names and counts depend on the artifact class
and evidence. The exercise supplies one small profile; the study's broader
synthesis supplies the recorded candidate inventory examined in chapter 4. Original
observations and profiles remain available when a proposed consolidation
needs to be reconsidered.

## Implementation options

The standard library is sufficient for the supplied exercise. For a larger
collection, table libraries can provide the same explicitly defined grouping
and distinct-count operations. Representative evidence lists may need bounded
summaries, with the full observations retained separately. Similarity analysis
or splitting synthesis into multiple requests would be proposed extensions;
neither is necessary for this exercise or established by its results.

## Common mistakes

- Exact-name grouping can silently become semantic normalization if names are rewritten first.
- Repeated observations from one artifact can be counted as additional supporting snapshots.
- A subset's 100% support can be mistaken for full-collection coverage.
- Representative field names can be mistaken for exhaustive concept assignments.
- A candidate concept inventory can be treated as an accepted schema or formal ontology.

## Verification

- The profiling command produces the quoted counts and retains all input records unchanged.
- Occurrence, distinct-snapshot, exact-name, and later concept-level statistics retain their separate units and denominators.
- The title comparison states a similarity and an unresolved distinction, and synthesis stops at the recorded candidate output.
