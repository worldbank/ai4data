# 1. Artifact Characterization and Sampling

**Question:** What must the schema describe, and which artifacts provide credible evidence of its requirements?

## Rationale

An artifact is the object for which a metadata record is being designed. A
Data Snapshot can be a table, chart, map, or composite analytical figure that
people need to find and interpret independently of its parent document. Its
metadata describes what it represents. The individual numerical observations
inside it are analytical content. A schema that describes a whole report can
miss the different indicators, populations, and periods of its individual figures.

The artifact class must be characterized before discovery begins. Otherwise,
a model can propose reasonable properties for an unintended object: a PDF,
a table cell, or an entire monitoring project. Sampling then supplies evidence
about the variation that the schema must accommodate. An identifiable frozen
selection makes later transformations traceable; a separate held-out selection
provides evidence for the validation developed in [chapter 6](./validation.mdx).

## Target state

- A characterization statement identifies one artifact, its boundaries, intended uses, and excluded contents.
- A fixed register identifies development and held-out artifacts, their sources, and the diversity considered.
- Identity checks distinguish snapshot overlap from parent-document overlap and state the limits of the selection.

## Learning objectives

- The practitioner can distinguish artifact metadata, analytical contents, and parent-document metadata.
- The practitioner can choose sampling dimensions and preserve an attributable selection.
- The practitioner can explain the unit at which development and validation evidence are separate.

## Prerequisite concepts

The organization has an intended use and access to candidate artifacts and
their source references. A domain reviewer understands the reporting context.
The exercises use Python 3.10 or newer and require no external packages.

## Maturity levels

| Level | Steps |
|---|---|
| **Foundational** | A human-readable characterization and reviewed selection establish the descriptive practice. |
| **AI-ready** | Structured identities, provenance, and documented checks make the selection usable by software. |
| **AI-native** | Model-assisted characterization has recorded evidence and verification, while humans decide scope and sample boundaries. |

## Recipes

<Recipe title="1.1 Define the artifact class and descriptive scope" level="Foundational" skills="Domain reviewer; technical practitioner" time="30–60 minutes for a first statement">

**Result:** A characterization statement establishes the object described, the intended descriptive uses, and the boundary with analytical contents and document metadata.

The statement defines the task given to the model. It should allow a reviewer
to decide whether an observation concerns the selected artifact. It establishes
purpose and scope without prescribing the metadata field inventory that
discovery will investigate.

The downloadable [characterization statement](pathname:///cookbook-files/ai-assisted-metadata-schema-development/artifact_characterization.md)
is a filled teaching worksheet with questions that can be reused for another
artifact class. Its entries restate the paper's scope; they are not a recovered
historical worksheet.

**Input example.** The Jordan snapshot is a bar chart titled “Figure 2:
Share of food expenditure in total expenditure p.c. (%).” The title describes
its subject. A sequence of bar values would be analytical content. The parent
document title, “Jordan - Emergency Food Security Project,” supplies context
but is not the chart title. The discovery observation for geographic scope
explicitly says that Jordan was inferred from document context and was not
visible in the snapshot. That distinction must survive later aggregation.

1. Identify one complete unit of description. State how a reviewer recognizes its boundary and what remains outside it. A multi-panel figure can be one snapshot even when its panels differ.
2. Name the intended uses, such as cataloging an analytical object, filtering by its subject, or finding evidence about an indicator. Explain which information would help those uses.
3. Compare three candidate properties: a description of the artifact, a numerical value within it, and administrative information about its parent document. State where each belongs.
4. Record allowed supporting context, exclusions, a reviewer, and a version. Inspect a contrasting artifact before accepting the statement. A useful statement remains applicable across the class.

**Worked example.** Applying those boundaries gives the following teaching decisions.

| Boundary question | Filled teaching decision |
|---|---|
| What receives one record? | The selected analytical snapshot receives the record. |
| What should be discoverable? | The record should identify and describe the snapshot's subject, context, and relevant provenance. |
| What is excluded from this task? | Reconstructing individual bar values or a complete data series is excluded. |
| How is document context handled? | Context is separately attributable, and document administration remains associated with the parent record. |

**Verification.** A second reviewer should be able to classify the chart title,
bar values, and parent-document title using the statement. A disagreement about
the object boundary is resolved before discovery requests are prepared.

**What this does not do.** The statement does not establish the final field
list or prove that a candidate value is correct. The filled decisions are a
teaching restatement of this application; another artifact class needs its own
scope and rationale.

</Recipe>

<Recipe title="1.2 Inspect a representative collection and freeze its sample" level="AI-ready" skills="Domain reviewer; Python practitioner" time="1–2 hours for a small accessible collection">

**Result:** A frozen sample register identifies the development artifacts, their provenance, the diversity represented, and the rationale for their inclusion.

Sampling should expose different descriptive requirements. Source institutions,
reporting purposes, artifact forms, and analytical contexts can all matter.
An identical count from each group does not establish statistical
representativeness. It is a deliberate coverage choice whose adequacy depends
on the intended application.

**Worked example.** The recorded study used the following development allocation.
Each corpus contributed 35 figures and 35 tables. These counts describe one
execution designed to expose semantic diversity across reporting contexts.

| Corpus | Figures | Tables | Total |
|---|---:|---:|---:|
| UNHCR / ReliefWeb | 35 | 35 | 70 |
| Policy Research Working Papers | 35 | 35 | 70 |
| Refugee Project Appraisal Documents | 35 | 35 | 70 |
| Total | 105 | 105 | 210 |

The [source-image register](pathname:///cookbook-files/ai-assisted-metadata-schema-development/source_images.csv) is a verified excerpt
of the research selections, enriched with public source links and reuse notes.
Its eight rows are sufficient for the local identity exercise. The complete
sampling statistics remain in the [research evidence](pathname:///cookbook-files/ai-assisted-metadata-schema-development/evidence.json),
under study_summary. The dataset revision is
626f3c54ba6d8f6e0ba0795f9e544e24b2650faf.

| Register column | Meaning in the exercise |
|---|---|
| snapshot_id | This exact dataset filename identifies the selected artifact. |
| split | The recorded role is development or heldout. |
| corpus and artifact_type | These identify source grouping and figure/table membership. |
| parent_document_id | This identifies the parent within its corpus. |
| hf_image_url and hf_metadata_url | These pin the image and document context to a public dataset revision. |
| original_record_url and original_pdf_url | These retain the institutional provenance supplied by the dataset metadata. |

1. Inventory the available artifacts and identify likely sources of variation. Consider document families, figure and table forms, reporting styles, languages, and specialized analytical contexts.
2. Inspect examples from contrasting groups. Record why each group might introduce a descriptive requirement that another group would miss.
3. Select and freeze the development identities. Preserve the realized selection even when sampling uses randomness; a seed alone cannot recover a changed source collection.
4. Record exclusions and limited groups. Reserve validation identities separately, then retain a versioned register and the source revision used to resolve them.

**Verification.** Confirm that a selected identity resolves to the recorded
source, that the split has been preserved, and that the rationale explains both
included diversity and exclusions. The accompanying image register records
accessibility and redistribution limits; image downloading is unnecessary here.

**What this does not do.** The eight-row teaching excerpt cannot establish the
coverage of a new application. Neither eight nor 210 is a universal minimum.
Additional sampling needs a reason tied to uncovered diversity. An arbitrary
target count does not supply that rationale.

</Recipe>

<Recipe title="1.3 Check the development and held-out boundary" level="AI-ready" skills="Python practitioner; evaluation reviewer" time="15–30 minutes with prepared registers">

**Result:** An identity report states whether snapshots overlap and whether their parent documents are shared across the two collections.

Snapshot-level separation means that the same image identity is not used in
both collections. Parent-document separation is stronger in a different way:
it asks whether validation introduces documents absent from development.
Figures from one report can share terminology and presentation. The two
checks therefore support different interpretations of generalization.

**Inputs.** Place the downloadable
[manifest checker](pathname:///cookbook-files/ai-assisted-metadata-schema-development/check_manifest.py) beside source_images.csv in a new working directory. Run
the command below from that directory. The checker reads the eight rows, checks required
identity fields, and writes nothing.

1. Use one register row per snapshot with an explicit split and nonempty source identity. Check duplicate identities before counting support.
2. Compare snapshot identities across splits. Treat an overlapping identity as a selection error requiring review.
3. Compare parent identities using the pair of corpus and parent_document_id. A bare document identifier may be reused in different source collections.
4. Report both results with their units and the scope of the register. Keep the teaching excerpt's results separate from the full study.

**Worked example.** The supplied register produces the following identity report.

```bash
python check_manifest.py source_images.csv
```

```text
development: 6 snapshots, 6 parent documents
heldout: 2 snapshots, 2 parent documents
snapshot overlap: 0
shared parent documents: 0
```

**Recorded collection boundary.** The full manifests contain 210 development
snapshots from 132 parents and 202 held-out snapshots from 125 parents. They
have zero overlapping snapshots and 65 shared parents. Those full-manifest
comparisons were verified during evidence preparation and are labelled
separately in evidence.json. The two selected held-out objects do not happen
to share parents with the six selected development objects. That local result
cannot replace the full-manifest comparison.

The held-out collection contained 35 figures and 35 tables per corpus except
for Refugee Project Appraisal Documents, where 27 eligible figures remained.
The study tests additional snapshots from the selected reporting domains; it
does not establish performance on a wholly document-disjoint collection.

**Verification.** Expect the exact four output lines above for the supplied
excerpt and exit status 0. A duplicate identity, unknown split, or missing
identity value must produce a nonzero exit. Interpret shared parents explicitly;
do not silently relabel a snapshot-disjoint design as document-disjoint.

**What this does not do.** The script checks the supplied register only. It
does not evaluate semantic diversity, reconstruct the full study split, or
reserve new evaluation data. A future document-disjoint design is a proposed
extension with different selection requirements.

</Recipe>

## Expected artifact

The characterization statement and frozen register define the object, scope,
provenance, and selection boundary for [independent discovery](./discovery.mdx).
They do not prescribe its candidate field names.

## Implementation options

A spreadsheet is adequate for an initial reviewed selection. CSV and JSON
make identities easier to check programmatically. Model assistance can suggest
diversity dimensions, but such suggestions need source inspection and human
approval. Changing the artifact class or intended use can require revisiting
the characterization before increasing the sample.

## Common mistakes

- A report-level description can obscure different artifacts within the document.
- Numerical observations can be mistaken for the reusable descriptive properties this task investigates.
- Balanced group counts can be mistaken for statistical representativeness.
- Zero overlap in an excerpt can be mistaken for the boundary of the full collection.

## Verification

- Reviewers can explain the unit described and classify the three boundary examples consistently.
- Every selected identity retains its corpus, parent, split, and attributable source reference.
- The manifest command produces the quoted excerpt counts, while the full-study boundary remains separately identified.
