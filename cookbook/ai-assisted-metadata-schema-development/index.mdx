# Practical Guide to AI-Assisted Metadata Schema Development

**A cookbook to help technical practitioners start building a metadata schema for their own materials and use case.** Version 0.1 (working draft), November 2026.

:::note[Working draft]
This guide is a working draft from the AI for Data – Data for AI program.
All seven chapters contain substantive recipes and worked examples for
editorial review. Chapter 1 defines the scope and samples; Chapters 2–3 include
Python worked examples. Chapters 4–7 add concept review, field design,
validation decisions, and standards comparison.
The complete draft is ready for a coordinated editorial and technical review. It does not represent official World Bank Group guidance or policy.
Corrections are welcome through [GitHub issues](https://github.com/worldbank/ai4data/issues);
the [contributing page](./contributing.md) describes the review expectations.
:::

To help people find and use reports, datasets, images, or recordings,
organizations need a consistent way to describe them. A metadata schema defines
what information to record about each item. The challenge is deciding which
fields will be useful for the materials and the task at hand.

This cookbook guides practitioners from examples of their own materials to a
schema suited to their use case. AI can propose candidate fields, identify
related concepts, and help compare meanings or draft documentation. Human
reviewers make the schema decisions.

This cookbook adapts the approach presented in the Data Snapshot research paper
by Dy & Solatorio (2026), using that study as a worked example.

## Purpose and learning outcomes

- The practitioner can define what the schema needs to describe and select examples that reflect its intended uses.
- The practitioner can use AI to suggest and organize metadata fields, then review and refine those suggestions.
- The practitioner can write field definitions and usage guidance, then test and improve the schema using new examples.
- The practitioner can use relevant standards to refine the schema while preserving the requirements of their materials and use case.

## Prerequisites

- Manual review requires representative materials and a reviewer who understands their intended use.
- The response-inspection and profiling examples require Python 3.10 or newer and the ability to read CSV and JSON files. They use only the standard library.
- Hosted LLM execution requires suitable provider credentials and configuration, and may require paid access.
- Local LLM execution requires an available model, a compatible interface, and sufficient computing resources; provider API credentials may not be needed.

Running the supplied scripts on recorded study outputs needs no LLM credentials
or paid calls. The request examples describe logical tasks; adapt inputs and response checks to the chosen
interface before a new run. Rechecking standards requires authoritative sources.
New runs also need resource planning and checks against the materials.

## First steps

1. Read [chapter 1](./characterization.mdx) to define what gets a metadata record and select development and holdout examples. Allow about 30 minutes for reading and the scope worksheet.
2. Inspect metadata suggestions in [chapter 2](./discovery.mdx), then group names and propose concepts in [chapter 3](./concept-synthesis.mdx). Allow about 60–90 minutes for reading, response inspection, and the profiling example.
3. Review concepts and turn them into fields in [chapters 4](./concept-refinement.mdx) and [5](./schema-design.mdx). Allow about 60–90 minutes for reading and selected worksheet tasks.
4. Test the schema and review findings in [chapter 6](./validation.mdx), then compare relevant standards and refine the specification in [chapter 7](./standards-refinement.mdx). Allow about 90–120 minutes for reading and selected evidence checks.

These are indicative reading and worked-example estimates. Applying the
methodology to a new collection requires sampling, domain review, standards
research, and additional work.
The [self-assessment](./start-here.mdx) provides one checkpoint per chapter.

## Maturity levels

An organization can reach different levels in different chapters. Human review
remains necessary at every level. Greater automation does not grant authority
to accept schema changes.

| Level | Meaning |
|---|---|
| **Foundational** | The practice exists in a form a person can use and a crawler can read. Practitioners inspect evidence and record human decisions. |
| **AI-ready** | The practice is structured, identified, and accessible through documented interfaces. Observations, mappings, and decisions support repeatable checks. |
| **AI-native** | AI-oriented methods have provenance and verification built in. Bounded model assistance supports discovery, comparison, and assessment under human adjudication. |

## Running example

The running example comes from a real use case examined by Dy & Solatorio
(2026): developing a metadata schema for data snapshots, such as tables, charts,
and maps from reports. The chapters follow selected examples and decisions from
that study. Source images and document metadata are available in the
[public dataset](https://huggingface.co/datasets/ai4data/data-snapshot).

## Scope of the examples

Recorded study results, selected excerpts, preparation-time deterministic worked
examples, and proposed extensions retain distinct labels. A simplified example
does not claim an independent execution of the study. The study sample size
is not a universal minimum.

The evidence supports bounded conclusions for the tested collections. It does
not establish universal generalizability, superiority over alternatives, or a
false-negative rate. Production metadata extraction, document layout detection,
formal ontology construction, and knowledge graph infrastructure are outside
this guide. Post-study machine-readable implementation remains separate from
the research endpoint.
