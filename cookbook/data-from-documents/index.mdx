# Practical Guide to Extracting Data from Documents

**A cookbook for dissemination, library, and research data teams.** Version 0.1 (working draft), October 2026.

:::note[Working draft]
This guide is a working draft from the AI for Data – Data for AI program. It
collects practical approaches and open standards. It does not
represent official World Bank Group guidance or policy and is not legal
advice; an organization applies it under its own statistical law, data
protection rules, and institutional policies.
Comments and corrections are welcome as
[GitHub issues](https://github.com/worldbank/ai4data/issues), and the
[contributing](./contributing.md) page explains how to propose a recipe.
:::

A large share of the statistics a national statistical organization has
ever published exists only inside documents: reports, bulletins, yearbooks,
census volumes. The tables and charts in them are read by people and copied
by hand. Software cannot query them, an AI system that reads the PDF will
transcribe them with errors, and nothing links a number quoted from a
report back to the page it came from.

This guide is organized around nine questions that a team can ask about
the data in its documents. The questions follow the order of the work.
The first two are about the documents themselves: which of them hold
data, and whether scanned documents can be read reliably. The next three
are about getting the data out: whether the tables and figures can be
located, whether the data can be extracted into a structured form, and
whether the extracted values can be verified against the document. The
last four are about what happens afterwards: whether tables from many
documents can be combined into one series, whether the data can be
published next to the document with their provenance, whether they can
be found and cited back to the page, and whether the pipeline can run
over the whole backlog. Each chapter answers one question with recipes,
maturity levels, worked examples, and a checklist.

The recipes build on the program's Data Snapshots work, which benchmarks
open-source layout detection models on institutional documents and
publishes the annotated dataset, and on the World Bank document and table
schemas, which hold the records for a document and for a table extracted
from it. The [standards page](./standards.md) lists each standard and where
it applies.

:::tip[Verification before publication]
An extracted value without a check is a transcription. The recipes in
[chapter 5](./verify.mdx) use what the document itself offers (printed value
labels, row totals, derived rates) to verify values, and the tidy files
carry the result per value. Values that cannot be verified are published
as estimates and say so.
:::

## Prerequisites

The recipes assume the following are in place or can be arranged:

- The publications the organization has produced, as PDF files, and a list of them (a publication register or a folder).
- A person who can run Python scripts and install open-source tools (OCR engines, layout models), and a dissemination officer who knows which tables users ask for.
- For the AI-ready level, a machine with a GPU or patience for layout detection, and access to a vision-language model for charts; for the AI-native level, a developer to run the pipeline.

## First steps

For a team with limited time, this sequence gives the most useful result first:

1. Build the inventory of [chapter 1](./inventory.mdx). It takes a day, and it says where the data are, which files are scans, and how large the work is.
2. Pick the five most requested tables, extract them from the text layer as [chapter 4](./extract.mdx) describes, and run the verification of [chapter 5](./verify.mdx). This takes two days. Then publish them next to the documents with their provenance, following [chapter 7](./publish.mdx).
3. For scanned documents, run OCR on one priority document and score it, following [chapter 2](./scanned.mdx), before investing in the rest.

Layout detection ([chapter 3](./locate.mdx)), series across documents ([chapter 6](./series.mdx)), and the pipeline ([chapter 9](./operate.mdx)) come once the first tables are published and used.

## Self-assessment

The [self-assessment](./start-here.mdx) takes about five minutes and places
a document collection at a level in each chapter.

## Maturity levels

Each chapter describes three levels. A document collection can sit at
different levels in different chapters, and the first level is a complete,
useful state on its own.

| Level | Meaning |
|---|---|
| **Foundational** | The documents are inventoried and catalogued, with a text layer, and their data are extracted by hand where needed. |
| **AI-ready** | Tables and figures are located and extracted with tools, verified against the document, and published as tidy files with provenance next to the document. |
| **AI-native** | Extraction runs as a pipeline on new documents, extracted data are catalogued and searchable, and every value cites its page and bounding box. |

## Running example

The recipes use two documents. The first is real: page 12 of World Bank
Policy Research Working Paper 4771, from the `data-snapshot` dataset, with
a bar chart whose values are printed on the bars; the same page is the
example on the program's home page. The second is fictional: the Food
security report 2025 of the example organization (`EX-REP-2025-03`), with a
district table in which one value is planted as an extraction error. A
small document inventory of eight fictional documents, one OCR page of
the fictional 2014 census report with planted recognition errors, two
extracted tables from successive food security reports, and a processing
log complete the example. All values of the fictional documents are
invented.

## Scope of the examples

The examples are small on purpose: one chart, one table, eight documents,
so that a reader can run them in an afternoon and see the shape of each
check. They are starting points. Each recipe ends with a **What this does
not do** note that says where the example stops and what the full version
adds. The scripts handle the structured outputs; the extraction itself
(layout detection, table parsing, chart reading) uses the tools named in
each chapter.
