# 7. The re-assessment

**Question:** How is progress measured at the re-assessment?

## Rationale

The framework describes readiness scores as baselines for action, and it
says that repeat assessments can be scheduled as an organization's
readiness matures. A re-assessment at the end of the cycle is where the
pathway is measured: the same questions, answered with the evidence the
register produced, give a second profile, and the comparison of the two
says which targets were reached and which questions moved.

Two cautions come from the framework itself. Scores across versions of
the framework are not directly comparable, so the re-assessment uses the
same version as the first assessment or notes the difference. And the comparison is a planning result. A dimension that did not reach its target is the first candidate for the next cycle, and a question that moved down is a finding to read.

## Target state

- The re-assessment is scheduled at the end of the cycle on the same framework version, with the evidence register as its pack.
- The two profiles are compared by script, per dimension and per question.
- The targets reached and missed are known, and the questions that moved down are read.
- The comparison opens the next cycle's target setting.

## Maturity levels

| Level | Steps |
|---|---|
| **Foundational** | Re-assess on the same version with the evidence pack; compute and compare the profiles. |
| **AI-ready** | Read the questions that moved down and the targets missed with their owners; set the next cycle's targets from the comparison. |
| **AI-native** | Publish the comparison with the pathway and contribute it to the peer network's evidence base, with country identification as the organization chooses. |

:::info[Running example]
The example organization was re-assessed on 2026-09-30, fifteen months
after its first assessment. Its overall score rose from 25.6 to 55.3,
every target was reached, fifty-one questions moved up and none down. The
file is
[scores_after.csv](pathname:///cookbook-files/assessment-to-pathway/scores_after.csv).
:::

## Recipes

<Recipe title="7.1 Re-assess with the evidence pack" level="Foundational" skills="The assessment's coordinator with the owners of each dimension" time="The assessment's own duration">

**Result:** a second score file, on the same framework version, answered
with the documents the evidence register names.

The re-assessment is the first assessment repeated, with one difference:
the organization arrives with a pack. For each question the evidence
register names the document that answers it, and the assessor reads the
document. The pack makes the re-assessment shorter and its answers
defensible, and it is what the register was for.

1. Confirm the framework version. Where a newer version is used, note the
   questions that changed, because their scores will not compare.
2. Export the evidence register with the location of each document as
   the pack, in question order.
3. Answer each question from the document, with the assessor's note
   where the document and the response option do not match exactly.
4. Enter the answers in a second score file with the same questions.

**Worked example.** The example organization's re-assessment on 2026-09-30
used the same version as its first assessment. Its pack listed the document and its location for each of the forty-six rows. Among them were the policy on the methods page, the register and the risk register in the governance repository, the DOIs on the catalog, the licence fields in the records, the API documentation, and the MCP pilot's manifest. The assessor answered
the questions from the documents, and the notes record two cases where
the document existed and the response option asked for more.

**What this does not do.** The pack shows what exists. The assessor's
reading of each document against the response options is the score, and
the organization's own expectation of a score is not evidence.

</Recipe>

<Recipe title="7.2 Compare the two profiles" level="Foundational" skills="A planning officer who can run a Python script" time="Fifteen minutes">

**Result:** per dimension, the level and average before and after,
whether the target was reached, and the questions that moved up and down;
and the pillar and overall scores for both.

1. Run the comparison with the two score files and the targets.
2. Read the targets missed first, then the questions that moved down.
   Each is a finding with an owner.
3. Read the overall change last, as the summary for the board and the
   funder.

```bash
python compare_profiles.py question_scores.csv scores_after.csv targets.csv
```

**Worked example.** The example organization reached every target.
Metadata standards rose to an average of 2.20, with one question at D,
because the organization regenerated its records from production, which
was a D recipe it added in the second wave when the developer had time.
The technical environment rose to C without a target above B, carried by
the model server and the evaluation suite the other dimensions needed.
Agentic access reached B with three of five questions moved, the MCP
pilot and the assistant's grounding among them; the ML-ready dataset and
the synthetic file stayed at A and open the next cycle. The overall score
rose from 25.6 to 55.3.

**What this does not do.** A comparison on the same version is a planning
result. The framework warns against reading scores as a ranking, and the example organization's rise says what its pathway did. It says nothing about where the organization stands against any other.

</Recipe>

<Recipe title="7.3 Open the next cycle from the comparison" level="AI-ready" skills="The planning team with management" time="Half a day">

**Result:** the next cycle's target table starts from the comparison,
with the targets missed, the questions still at A, and the frontier
dimensions the foundations now allow.

The comparison is the first page of the next pathway. A target missed
keeps its target, with a reason that says what stopped it. A question
that stayed at A in a dimension that reached its target is the next
cycle's first row in the evidence register. A frontier dimension whose
dependencies are now at target can move.

1. Carry the targets missed into the new target table, with a reason.
2. List the questions still at A or B in dimensions at target, and set
   the next targets so that they move.
3. Re-run the sequence: dimensions that reached their target leave the
   waves, and the frontier dimensions enter.
4. Record the new targets as the board's decision, and start chapter 2
   again.

**Worked example.** The example organization's next cycle sets C for
agentic access, now that the API, the licences, and the governance are
at C, and names the ML-ready dataset and the synthetic file as its first
evidence rows. It sets C for skills, with the recruitment of a data
scientist that the first cycle left out, and C for funding, with
lifecycle funding for the components the first cycle built. The
foundations stay at C with reasons that name the D recipes as options
for the cycle after.

**What this does not do.** The next cycle's pathway is a new pathway,
with its own estimate and its own approval. The comparison says where to
start; the chapters of this guide say how.

</Recipe>

## Implementation options

- **Version changes.** Where the framework's version changed between assessments, compare only the questions that both versions ask, and note the rest.
- **Sharing results.** The program's global survey and peer network aggregate situational information without country league tables; an organization can contribute its comparison on the same terms.
- **Publication.** The comparison's summary can be published with the pathway, as a statement of what the organization set out to do and what it did.

## Common mistakes

- **A re-assessment on a different version, compared anyway.** The framework says the scores are not comparable; the note is the only honest comparison.
- **A re-assessment without the pack.** The assessor scores what is shown, and an organization that forgot its documents scores as if it had none.
- **Reading the overall score first.** The targets missed and the questions that moved down are the findings.
- **A comparison that ends the cycle.** It starts the next one.

## Verification

- **Version check.** Both score files carry the same framework version, or the differing questions are noted.
- **Comparison check.** The script passes, and every target missed and every question that moved down has an owner's note.
- **Continuity check.** The next cycle's target table exists and starts from the comparison.
